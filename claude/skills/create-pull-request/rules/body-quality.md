# PR 正文品質

適用於**每一份** PR 描述，不管長成兩節還是七節。

## 五條原則

- **寫 why，不寫 what。** diff 已經顯示改了什麼；描述要補的是動機、限制條件、以及程式碼裡看不見的權衡。
- **不覆述 diff。** 逐檔列「改了 X、改了 Y」對 reviewer 沒有價值，他正要去看那份 diff。
- **連結相關 issue。** 用 `closes #123` / `fixes #456`，merge 時 GitHub 會自動關閉。
- **標出棘手處。** reviewer 可能漏掉的東西——微妙的不變式、刻意的取捨、已知的限制——主動點出來。
- **沒東西寫的章節直接刪掉。** 空的 `Notes` 或 `Risks` 是噪音。

第五條最常被違反，因為刪掉一節看起來像偷懶。實際上相反：**保留一個寫著「N/A」的 Security 章節，會讓下一個讀者以為安全性被評估過了。** 空章節不是中立的，它會製造假訊號。

## Review 一份現成的 PR 描述

- [ ] 解釋了 **why**，不只是 **what**
- [ ] 沒有把 diff 用散文重念一遍
- [ ] 相關 issue 有連結
- [ ] 棘手處有標出來給 reviewer
- [ ] 空的樣板章節已經刪掉
- [ ] 該長出來的章節有長出來（對照 `templates/pr-body.md` 的觸發條件表）

最後一條是唯一需要看 diff 才能判斷的——前五條看描述本身就夠。一份漏掉 Security 的 auth PR，光讀描述完全看不出問題，只有把描述跟 diff 對起來才會發現。

## 寫不出 why 的時候

代表你不知道這個分支為什麼存在。**去問，不要編**——編出來的動機比空白更有害，因為 reviewer 會當真，並且用它來判斷該把注意力放哪。

在問之前先確認答案是不是已經躺在 repo 裡：分支上的 commit 訊息（如果照 `commit-message` 寫，WHY 已經在裡面）、關聯的 issue、或 diff 本身透露的限制條件。多數情況下 PR 的 why 就是把分支上各個 commit 的 WHY 收攏成一句。

# 拆分判準

## 唯一的判準

**這些變更能不能用一句 WHY 講完？**

不能，就該拆。這條判準比「檔案數量」「行數」「有沒有動到不同目錄」都準確，因為它直接指向提交訊息的品質——一個寫不出單一 WHY 的提交，未來的讀者也讀不出單一結論。

下面五個信號都是這條判準的具體表現，用來快速偵測，不是獨立規則。

## 五個該拆的信號

### 1. 混了不同的變更類型

同一批變更裡既有 `feat` 又有 `fix`，或既有 `refactor` 又有 `chore`。type 選不出來本身就是信號——**你猶豫該標 feat 還是 fix，通常是因為兩件事都做了**。

### 2. 動到不相關的領域

改了 auth 又順手改了 CI 設定。它們的 WHY 完全無關，未來要 revert 其中一個時會被綁死。

### 3. 噪音變更混進實質變更

這三類一律獨立提交：

- 純格式化 / linter 自動修復
- 依賴升級（`go.sum`、`package-lock.json`、`Cargo.lock`）
- 大規模重新命名或檔案搬移

它們產生的 diff 量會淹沒真正的邏輯變更，讓 review 的人找不到重點。搬檔案尤其要獨立提交，否則 `git log --follow` 追不到歷史。

### 4. 有一部分可以獨立驗證

如果變更 A 不需要變更 B 就能通過測試，它們就是兩件事。這條也是實務上最有價值的一條——**可獨立驗證 = 可獨立 revert**。

### 5. 你在寫 WHY 時用了「順便」「同時」「另外」

語言會誠實地洩漏結構。正文出現這些連接詞，表示你正在把兩個動機接起來。

## 不該拆的情況

判準是對稱的——強行拆開一件事，跟把三件事塞在一起同樣有害。

- **拆完會留下不能編譯或測試不過的中間狀態。** 每一筆提交都必須能獨立 build。這條優先於上面所有信號。
- **變更跨領域但邏輯上是同一件事。** 例如一次 API 欄位改名同時動到後端 handler、前端呼叫端與測試——這是一個 WHY，一起提交，並在 HOW 裡說明為什麼不能分開。
- **拆出來的提交小到訊息比 diff 長。** 這是形式主義，不是原子性。

## 拆分後的暫存手法

```bash
git add <file> ...        # 整檔屬於同一主題時
git add -p                # 同一個檔案裡混了多個主題時，按 hunk 挑
git add -N <new-file>     # 新檔案要用 -p 挑之前先讓 git 認得它
```

分批提交時，每批做完 Step 4–6 一整輪再處理下一批，不要先全部暫存再想辦法拆——`git add -p` 之後 diff 的 hunk 編號會變，一次處理一批最不容易出錯。

暫存完、提交前跑一次 `git diff --cached --stat` 確認這批的內容真的只有預期的檔案。

## 怎麼跟使用者提

拆分是**建議，不是代替他決定**。提出時要具體到可以直接執行：

```
這批變更看起來是三件事，建議拆成：

1. fix(auth): prevent token refresh race        ← auth/token.go, auth/token_test.go
2. chore: bump golang.org/x/crypto to v0.31.0   ← go.mod, go.sum
3. style: apply gofmt to cmd/                    ← cmd/ 下 8 個檔案

要照這樣拆嗎？還是一起提交？
```

列出每筆的標題與對應檔案，使用者才能一眼判斷你拆對了沒有。只說「建議拆成三個提交」，他無從判斷。

他選擇一起提交時就照做，不要再勸第二次——他可能有你不知道的理由（要 cherry-pick、要對應某個 ticket、待會就要 squash）。

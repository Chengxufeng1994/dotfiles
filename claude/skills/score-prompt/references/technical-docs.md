# 情境：技術文件

適用於 API 文件、README、架構說明、operation runbook、新人上手指南——**產出物是要被工程師拿去做事的參考資料。**

## 這個情境的五維重心

| 維度 | 在這類任務裡特別重要的原因 |
|---|---|
| **S** | 讀者的既有知識水位是最關鍵的事實。寫給團隊新人和寫給外部整合者，是兩份不同的文件 |
| **C** | 決定文件的組織邏輯——讀者視角 vs 系統架構視角，差別極大 |
| **O** | 用「讀者在多久內能完成什麼」來定義，比「寫一份完整文件」有用得多 |
| **R** | 章節順序本身就是設計。快速開始要在最前面還是認證要在最前面，取決於 O |
| **E** | 重心不在字數，在**可執行性**：範例能不能直接跑、錯誤碼有沒有涵蓋完 |

**最容易寫壞的一維是 C。**「你是一位資深工程師」通不過替換測試。有作用的角色是「習慣從讀者第一次串接的視角組織內容，而不是從系統架構的視角」——這句話會實質改變章節的排法。

## 問答選項設計要點

**情境那題**沿「讀者是誰」分化，因為它決定了要假設多少既有知識：

- A（推薦）團隊新人：內部服務，讀者是剛加入的後端工程師，已有 OpenAPI spec 但缺敘述型文件
- B 外部整合者：公開 API，讀者不了解我們的領域術語與業務流程
- C 未來的自己／交接對象：內部系統，重點在為什麼這樣設計，而非怎麼呼叫

**目標那題**要用可測量的上手成效，而不是文件完整度：

- A（推薦）讓沒碰過這個服務的工程師，在 30 分鐘內完成第一次成功呼叫
- B 讓整合方在不問我們任何問題的情況下自行完成串接
- C 讓接手維護的人理解當初的設計取捨，避免重蹈覆轍

**限制那題**要用可執行性當判準：

- A（推薦）每個 endpoint 附可直接執行的 curl 範例，錯誤碼表需涵蓋所有 4xx／5xx
- B 只寫成功路徑，錯誤處理另開章節
- C 需同時提供 curl 與 Go client 兩種範例

## 完整範例

### 原始需求
> 幫我寫一份 API 的使用說明

### SCORE 拆解

| 維度 | 內容 |
|---|---|
| **S** 情境 | 內部訂單服務的 REST API，讀者是剛加入的後端工程師；公司已有 OpenAPI spec 但沒有敘述型文件 |
| **C** 角色 | 寫過多份公開 SDK 文件的資深後端工程師，習慣從讀者第一次串接的視角組織內容 |
| **O** 目標 | 讓一位沒碰過這個服務的工程師，在 30 分鐘內完成第一次成功的下單呼叫 |
| **R** 產出 | Markdown 文件，含：快速開始、認證方式、每個 endpoint 的請求／回應範例、錯誤碼表 |
| **E** 限制 | 每個 endpoint 附可直接執行的 curl；錯誤碼表涵蓋所有 4xx／5xx；內部術語第一次出現必須先定義 |

### 成品 Prompt

```
## 情境
這是一個內部的訂單服務 REST API。讀者是剛加入團隊的後端工程師，對我們的業務領域還不熟。公司已有 OpenAPI spec，但缺少能引導人上手的敘述型文件，所以新人往往得靠問人才能完成第一次串接。

## 你的角色
你是一位寫過多份公開 SDK 文件的資深後端工程師。你習慣從「讀者第一次串接」的視角組織內容，而不是從系統架構的視角——也就是說，你會先讓人跑通一個最小案例，再回頭補全概念，而不是先講完所有名詞才給範例。

## 任務目標
讓一位完全沒碰過這個服務的工程師，能在 30 分鐘內完成第一次成功的下單 API 呼叫。所有章節的排序與詳略都以這個目標為準。

## 輸出要求
產出一份 Markdown 文件，依序包含：
1. 快速開始 — 從取得憑證到跑通第一個請求的最短路徑
2. 認證方式 — 憑證怎麼取得、怎麼帶、多久過期
3. 各 endpoint 的請求與回應範例
4. 錯誤碼表

## 限制條件
- 每個 endpoint 必須附一段可直接複製執行的 curl 範例，含完整 header
- 錯誤碼表需涵蓋所有 4xx 與 5xx 情況，每個錯誤碼要說明「什麼情況會發生」與「該怎麼處理」
- 任何內部術語第一次出現時必須先用一句話定義
- 回應範例使用真實形狀的假資料，不要用 `string`、`foo` 這類佔位值
```

### 自檢

- ✅ **Exactness 可驗證**：「每個 endpoint 有 curl」「錯誤碼完整」「無未定義術語」都可逐項核對
- ✅ **Objective ≠ Result**：O 是「30 分鐘內完成第一次呼叫」這個成效，R 是四個章節
- ✅ **Character 有作用**：讀者視角與架構視角會產出組織方式完全不同的文件
- ✅ **Result 有骨架**：章節順序明確，且順序本身服務於 O
- ⚠️ **Situation 資訊仍不足**：未說明認證機制是 JWT 還是 API key，寫作時仍需猜測，建議補上
- ⚠️ **五維無矛盾**：若 endpoint 數量超過 20 個，「每個都附 curl」會讓文件過長，建議改成「核心 5 個附完整範例，其餘只列簽章」

## 這個情境的常見陷阱

**目標寫成「文件要完整」是無效的。**完整是無底洞，而且完整的文件常常最難上手。改用「讀者在 X 時間內能完成 Y」，章節取捨才有依據。

**Situation 沒交代讀者的知識水位，就會寫出兩頭不到岸的文件。**要嘛預設太多（新人看不懂）、要嘛從零解釋（老手嫌囉嗦）。這一格務必問清楚。

**Exactness 要包含「範例的真實度」。**「回應範例使用真實形狀的假資料」這條看似瑣碎，但少了它，模型很容易產出 `{"data": "string"}` 這種對讀者毫無幫助的範例。

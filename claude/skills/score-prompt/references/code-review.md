# 情境：程式碼審查與技術評估

適用於 PR review、重構建議、架構評估、技術選型比較——**產出物是要推動某個技術決定往前走的判斷。**

## 這個情境的五維重心

技術任務裡五維的語意會整體移位，這是它與其他情境最大的差別：

| 維度 | 在技術任務裡變成什麼 |
|---|---|
| **S** | 技術棧、既有架構、CI 已經涵蓋什麼、團隊規模與 review 文化 |
| **C** | 不是文案角色，而是**審查視角**——tech lead、安全專家、架構師會看見完全不同的問題 |
| **O** | 「攔截什麼」＋「讓作者知道什麼」，而不是「產出一份 review 報告」 |
| **R** | 嚴重度分級 ＋ 每項的固定欄位（位置／問題／風險／建議） |
| **E** | 可編譯、有行號、有分級、有數量上限、不重複 linter 已涵蓋的事 |

**S 有一個技術情境獨有的高價值用法**：交代 CI 已經在跑什麼。因為只要說明「CI 已跑 gofmt 與 golangci-lint」，就能理直氣壯地在限制條件裡禁止模型評論格式問題——而格式 nit 洗版正是 AI code review 最常見的失敗模式。

## 問答選項設計要點

**情境那題**沿專案性質分化，因為它決定 review 的重心：

- A（推薦）團隊內部後端服務：Go 微服務，對外提供 HTTP／gRPC API，已有 lint 與測試在 CI
- B 開源 library／SDK：使用者是外部開發者，公開 API 相容性與 godoc 比內部實作重要
- C 基礎設施工具：CLI、Kubernetes controller、data pipeline，重點在資源管理與優雅關閉

**角色那題**要用審查視角分化，這一題通過替換測試的效果最明顯：

- A（推薦）10 年經驗的資深工程師／tech lead：熟悉併發、error handling、標準庫慣例；風格是「會出事的先擋下來，其餘標成建議，不糾結個人偏好」
- B 安全審查專家：重心在輸入驗證、注入、認證授權、機敏資料外洩、相依套件漏洞
- C 系統架構師：重心在套件邊界、相依方向、抽象是否過度，較少碰實作細節

**限制那題**的核心是**抑制噪音**：

- A（推薦）每項標 `檔案:行號` 並附可套用的修改片段；一律標 `[Blocker]`／`[Should fix]`／`[Nit]`；不評論 linter 能自動抓的問題；證據不足標「需作者確認」不臆測；總數上限 10 條
- B 不設上限，鉅細靡遺列出所有觀察
- C 只回報 Blocker，其餘全部略過

B 是實務上最糟的選項，值得在推薦理由裡點出來：nit 洗版會淹沒真正的 bug，讓 review 失去可信度。

## 完整範例

### 原始需求
> 幫我弄一個可以重複用的提示詞模板，用來讓 AI 幫我 review Go 專案的 pull request

### SCORE 拆解

| 維度 | 內容 |
|---|---|
| **S** 情境 | 團隊內部 Go 後端服務，提供 HTTP／gRPC API，會存取 DB 與外部服務；CI 已跑 golangci-lint 與單元測試；PR 多為功能開發與 bugfix |
| **C** 角色 | 10 年 Go 經驗的資深工程師／tech lead，熟悉 goroutine 生命週期、context 傳遞、error wrapping；先擋會出事的，其餘標建議 |
| **O** 目標 | merge 前攔截會進 production 出事的缺陷，並讓作者一眼看出哪些非改不可、哪些只是建議 |
| **R** 產出 | Markdown 報告：總評 → 判定 → 依嚴重度分級的問題清單（位置／問題／風險／建議）→ 值得肯定之處 → 下一步 |
| **E** 限制 | 每項須有 `檔案:行號` 與可套用的 Go 片段；三級標記；不評論 linter 可處理的問題；證據不足標「需作者確認」；上限 10 項 |

### 成品 Prompt

因為這是可重複使用的模板，固定的五維寫死，每次會變的 PR 資訊用 `{{ }}` 留空。詳見 `templates/reusable-prompt.md` 的變數槽設計。

````markdown
## 情境
我們是一個 2–8 人的後端團隊，維護一個以 Go 撰寫的服務，對外提供 HTTP／gRPC API，內部會存取資料庫與若干外部服務。Repository 的 CI 已經在跑 `gofmt`、`golangci-lint` 與單元測試，因此所有能被這些工具自動抓到的問題不需要你重複指出。進來的 PR 多半是功能開發或 bugfix，由團隊成員互相 review 後合併到主幹並部署到 production。

## 你的角色
你是一位有 10 年 Go 經驗的資深工程師兼 tech lead。你熟悉 goroutine 的生命週期與洩漏模式、`context` 的正確傳遞與取消、error wrapping（`%w`）與 `errors.Is`／`errors.As` 的使用時機、`defer` 的執行順序與常見陷阱、interface 應該定義在消費端、以及標準庫的慣例。

你的 review 風格是：**會讓 production 出事的問題優先擋下來，其餘標成建議，個人風格偏好不作為阻擋理由**。你講話直接但對事不對人，指出問題時一定同時給出可行的替代寫法。

## 任務目標
你的 review 要達成兩件事：
1. 在合併之前攔截真的會在 production 出問題的缺陷——特別是 data race 與並發安全、error 被吞掉或忽略、資源（DB 連線、檔案、HTTP body、goroutine、timer）沒有釋放、nil pointer／nil map 寫入、slice 邊界、context 沒有被傳遞或取消、以及沒有被測試涵蓋的新增分支。
2. 讓作者看完就知道**哪些非改不可、哪些改了更好、哪些只是順手提**，reviewer 能據此做出明確的 Approve 或 Request changes 決定。

成功的標準不是「產出一份完整的報告」，而是「作者不需要再問一次就知道下一步要做什麼」。

## 審查重點
依序檢查以下面向，只在**這個 diff 實際碰到**的部分發表意見：
1. **正確性**：邏輯是否符合 PR 描述的意圖？邊界條件（空 slice、nil map、零值、大量資料）是否處理？
2. **並發**：共享狀態是否有多個 goroutine 讀寫而未加鎖？goroutine 是否有明確的結束條件與 context 取消？channel 是否可能阻塞或洩漏？
3. **錯誤處理**：error 是否被忽略（含 `defer f.Close()` 這類吞錯誤的寫法）？是否用 `%w` 包裝並保留可判斷的錯誤型別？訊息是否含足夠上下文？
4. **資源管理**：`rows`、`resp.Body`、檔案、`ticker`、`context.CancelFunc` 是否都有對應釋放？`defer` 是否放在錯誤檢查之後？
5. **API 與相容性**：匯出的簽章是否有破壞性變更？新增公開 API 是否符合 Go 命名慣例、是否有 doc comment？
6. **測試**：新增或修改的邏輯有無對應測試？是否涵蓋錯誤路徑而不只是 happy path？
7. **安全**：是否有 SQL 字串拼接、未驗證的外部輸入、機敏資料寫進 log、不安全的預設值？（若發現，直接列為 Blocker。）
8. **可維護性**：函式是否過長或職責過多？抽象是否過度？命名是否表達意圖？（多屬 Should fix 或 Nit。）

## 輸出要求
輸出一份 Markdown 報告，依序包含：
1. **總評**：一句話說明這個 PR 做了什麼、整體品質如何。
2. **判定**：三選一並附一句理由——`Approve` ／ `Approve with comments` ／ `Request changes`。
3. **問題清單**：依嚴重度由高到低，每項格式為：
   - `### [嚴重度] 簡短標題`
   - 位置：`路徑/檔案.go:行號`
   - 問題：這裡發生了什麼
   - 風險：為什麼會出事，具體到什麼情況下會壞
   - 建議：可直接套用的 Go 程式碼片段
4. **值得肯定之處**：1–3 點，具體指出做得好的地方，不要寫空泛客套話。
5. **給作者的下一步**：兩三句，明確列出必須處理的項目編號。

## 限制條件
- 嚴重度只用三級，每項都必須標記：
  - `[Blocker]`＝會導致資料錯誤、當機、資安問題或線上事故，不修不能合併
  - `[Should fix]`＝不會立刻出事，但會累積成技術債或降低可靠度
  - `[Nit]`＝命名、註解、微小可讀性建議，作者可自行決定
- 每項問題都必須標明 `檔案:行號`；建議的程式碼必須語法正確、可直接貼進專案。
- **不要**評論 `gofmt`、`goimports`、`golangci-lint` 能自動處理的問題，CI 已經涵蓋。
- 只根據提供的 diff 與上下文判斷。若某個判斷需要看到 diff 以外的程式碼才能確定，標為「需作者確認」並寫出你需要知道什麼，**不要臆測**。
- 問題總數上限 10 項；超過時只保留最嚴重的 10 項，並在總評註明「另有較次要的建議未列出」。
- 若整個 PR 沒有 Blocker 或 Should fix，就直接說沒有，不要為了湊數製造 Nit。
- 全文繁體中文；技術名詞、識別字與程式碼保留英文。
- （可選開關，需要接自動化時再加上這行）另外附一份可直接貼到 GitHub 的行內 comment 清單，每則一行，格式為 `檔案:行號 — comment 內容`。

# 本次 PR 資訊（每次 review 只需替換這一區）

**PR 標題**：{{PR 標題}}

**PR 描述／解決的問題**：
{{作者寫的 description，或一句話說明這個 PR 想解決什麼}}

**相關背景**（可留白）：
{{例如：這段程式碼會被 X 服務高頻呼叫／這是為了修 #123 的線上事故／作者是剛加入的新人}}

**變更內容（diff）**：
```diff
{{在此貼上 git diff 或 GitHub Files changed 內容}}
```
````

### 自檢

- ✅ **Exactness 可驗證**：行號、三級標記、總數上限、有無提及 lint 可處理的問題，全部可逐條核對
- ✅ **Objective ≠ Result**：O 是「作者不必再問就知道下一步、reviewer 敢做決定」，R 是五段式報告
- ✅ **Character 有作用**：換成安全專家或架構師，同一份 diff 的 review 結果會明顯不同
- ⚠️ **Situation 有資訊量**：「CI 已跑 lint」這一句直接支撐了「不要評論格式問題」這條限制，很有效。但 Go 版本、專案 layout 與團隊風格指南是刻意留白的——為了保持模板泛用性；若你們有明文 style guide，把核心規則加進限制條件會讓 review 一致性再上一層
- ✅ **Result 有骨架**：五段結構＋問題項四欄格式都已指定
- ⚠️ **五維無矛盾**：「上限 10 項」與「八大審查面向」在超大型 PR 上會互相擠壓，此時會傾向只報 Blocker。若團隊常有大型 PR，建議改成「每個嚴重度各最多 5 項」

（六條各出現一次，刻意留白寫在對應維度的 ⚠️ 裡而不另立一行——見 `rules/quality-check.md`。）

### 使用建議

1. **第一次使用時**，把「情境」段改成你們專案的真實描述（服務做什麼、規模、CI 有什麼）。這是投報率最高的一次性投資，它會影響之後每一次 review 的準確度。
2. **每次 review** 只替換底部「本次 PR 資訊」區塊。diff 太長時優先貼核心變更檔案，並在「相關背景」註明省略了哪些（例如「已省略 generated code 與 go.sum」）。
3. **想改變 review 重心**時不要重寫整份模板，只換「你的角色」那一段即可——改成安全專家版或架構師版，其他四維完全共用。
4. **接進自動化**（GitHub Action、CI bot）時，加上限制條件的可選開關那行，輸出就會變成可解析的 `檔案:行號 — comment` 清單。

## 這個情境的常見陷阱

**沒有數量上限的 review 會變成噪音。**這是 AI code review 最常見的失敗：模型很樂意列出四十條觀察，其中三十五條是 nit，真正的 data race 被埋在第 28 條。上限與嚴重度分級一定要一起用。

**沒有交代 CI 涵蓋範圍，就無法正當地禁止格式評論。**「不要評論 gofmt 能處理的事」這條限制之所以站得住腳，是因為 Situation 說明了 CI 已經在跑。這是 S 與 E 互相支撐的典型例子。

**一定要有「不要臆測」的條款。**diff 是局部視野，模型看不到被呼叫端與呼叫端。沒有這條，它會用想像補完上下文，然後對著不存在的問題給出很有說服力的建議——這比漏掉問題更傷害信任。

**「值得肯定之處」不是客套。**它的實際功能是逼模型真的讀懂了 diff 在做什麼。寫不出具體的肯定，通常代表它其實沒看懂。

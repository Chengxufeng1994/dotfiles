# 情境：進度回報與對上溝通

適用於週報、月報、專案狀態更新、跨部門同步、向主管的請求說明——**產出物是要讓比你忙的人在極短時間內做出判斷。**

這個情境與商務書信的差別在於：書信要引起感受，進度回報要引起**判斷或行動**。讀者不是來欣賞的，是來決定要不要介入的。

## 這個情境的五維重心

| 維度 | 在這類任務裡特別重要的原因 |
|---|---|
| **S** | 要區分「穩定事實」與「本期素材」。團隊組成是穩定的，本週進度是每期變動的 |
| **C** | 決定資訊的濃縮比。資深 PM 與 Scrum Master 的取捨標準完全不同 |
| **O** | 幾乎都包含兩層：讓主管掌握進度（被動），以及讓主管看到某件事（主動） |
| **R** | 區塊固定化是這類文件的核心價值。每期同樣的骨架，讀者才能養成掃讀習慣 |
| **E** | 字數上限是最有效的一把尺，因為進度回報最大的失敗是寫太長沒人看 |

**這個情境有一個獨特的重點：Objective 通常有隱藏的第二層。**表面是「讓主管掌握進度」，實際上寫報告的人心裡往往還有一件事想讓主管看見——某個卡住的資源、某個需要決策的岔路、某個自己做得不錯但沒人注意的成果。問到這一層，報告的重心才會對。

## 問答選項設計要點

**情境那題**要同時問出團隊組成與回報節奏，並且提醒使用者：如果這是每週都要用的模板，本期的實際進度素材不該寫死在 Situation 裡，該放到變數槽（見 `templates/reusable-prompt.md`）。

**目標那題是這個情境的關鍵**，選項要拉出「被動掌握」與「主動促成」的差別：

- A（推薦）讓主管快速掌握整體進度，同時看見我對某個卡點的解決方案
- B 純粹同步現況，不需要主管做任何動作
- C 讓主管理解為什麼某項進度落後，並協助排除障礙

選 A 和選 B 會寫出結構相同但重心完全不同的報告。

**限制那題**用「字數 × 語氣 × 禁用詞」，其中字數最關鍵：

- A（推薦）500 字以內，語氣務實，不過度修飾
- B 300 字極簡，只列本期有變化的項目
- C 不限字數但每項須附連結或票號，供主管自行深入

## 完整範例

### 原始需求
> 我要寫這週的團隊週報給主管看

### SCORE 拆解

| 維度 | 內容 |
|---|---|
| **S** 情境 | 帶五人產品團隊，本週推進 A、B、C 三案：A 完成 80%、B 因資源不足受阻、C 尚未啟動 |
| **C** 角色 | 資深 PM，擅長把工作進度變成主管 30 秒可以看完的簡報 |
| **O** 目標 | 讓主管快速掌握進度，並且看見我對 B 的解決方案 |
| **R** 產出 | 條列式週報，四個區塊：本週成果、進度、下週計畫、需要協助 |
| **E** 限制 | 總字數 500 字以內，語氣務實，不要過度修飾 |

### 成品 Prompt

```
## 情境
我帶一個五人的產品團隊，這份週報每週寄給我的直屬主管。主管同時看好幾個團隊的報告，通常只在會議前快速掃過。

本週的狀況是：A 案完成約 80%，B 案因為資源不足而受阻，C 案尚未啟動。

## 你的角色
你是一位資深 PM，擅長把散落的工作進度濃縮成主管 30 秒就能看完的簡報。你的習慣是先講結論再講細節，並且會主動把「只是進度更新」和「需要主管介入的事」分開放。

## 任務目標
這份週報要達成兩件事：
1. 讓主管快速掌握三個案子的整體進度
2. 讓主管看見我對 B 案資源不足的解決方案——這一項是重點，不要淹沒在其他進度裡

## 輸出要求
產出條列式週報，依序包含四個區塊：
1. **本週成果** — 實際完成的事，用結果陳述而非過程陳述
2. **進度** — 各案目前狀態與完成度
3. **下週計畫** — 三項以內，只寫最重要的
4. **需要協助** — 明確寫出需要什麼、由誰提供、期限是什麼

## 限制條件
- 全文 500 字以內
- 語氣務實，不要過度修飾。不使用「順利推進」「大幅提升」「積極協調」這類沒有事實支撐的形容詞，改用具體數字或事件
- 沒有進展的項目直接寫沒有進展，不要用文字包裝
- 我沒提供的資訊一律標成 `[待補]`，不要自行推測補寫
```

### 自檢

- ✅ **Objective ≠ Result**：O 是「主管掌握進度並看見 B 案解方」這個認知結果，R 是四個區塊的條列週報
- ✅ **Exactness 可驗證**：字數、禁用形容詞、`[待補]` 標記都能逐條核對
- ✅ **Character 有作用**：換成「Scrum Master」會變成聚焦流程與依賴的內部文件，取捨標準完全不同
- ✅ **Result 有骨架**：四區塊明確，且「需要協助」區塊指定了三個必填欄位
- ⚠️ **Situation 混了兩種東西**：團隊組成（穩定）和本週三案進度（每週變動）寫在一起。如果這是每週要重複用的模板，把本週進度移到底部的變數槽，S 只留穩定事實——見 `templates/reusable-prompt.md`
- ⚠️ **五維無矛盾**：500 字要涵蓋四區塊、三個案子，偏緊。若某週案子變多，建議放寬到 800 字或改為「只寫本週有變化的項目」

## 這個情境的常見陷阱

**把本期素材寫死在 Situation 裡。**這是進度回報最常見的結構錯誤。「本週 A 完成 80%」是這一期的事實，不是情境。寫死了就等於每週都要改 prompt 的上半部，模板的價值消失一半。凡是使用者說了「每週」「每次」，就要主動把 S 拆成穩定層與變動層。

**Objective 只寫第一層。**「讓主管掌握進度」幾乎所有週報都適用，等於沒有指導性。要追問「這一期你最想讓他看見什麼」——那件事應該在報告裡有結構性的位置，而不是埋在第三個 bullet 裡。

**沒有禁用形容詞，報告會變成公關稿。**「順利推進」「積極協調」「大幅優化」是進度回報的通病：字數用掉了，資訊量是零。把這幾個詞明確列進禁用清單，比寫十句「要務實」有效。

**「需要協助」區塊沒有欄位就會流於空談。**「希望能有更多資源」不是請求，「需要一位前端工程師支援兩週，最晚下週三確認」才是。這個區塊務必指定三個必填欄位：需要什麼、由誰提供、期限。

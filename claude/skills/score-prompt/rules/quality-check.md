# 概念：品質檢核與反模式

自檢存在的理由，是**寫壞的 prompt 通常不是漏了某一維，而是某一維寫了但沒有作用**。五格全部填滿看起來很完整，實際上其中兩格是廢話——這種空轉從表面看不出來，只能靠逐項檢驗。

這份文件給每一項檢核一個**可操作的判斷動作**，而不只是一句標準。

## 六項檢核與一條原則

### 1. Exactness 可驗證 —— 用「驗收測試」

**動作**：假裝成品已經交來了，你能不能對著每一條限制打勾或打叉？

- 「300 字以內」→ 數字數，可以打勾
- 「不使用『敬啟者』『台端』」→ 搜尋，可以打勾
- 「語氣專業一點」→ 無法判定，✗
- 「內容要有深度」→ 無法判定，✗

無法驗收的限制不是限制，是願望。發現這種措辭時，把它翻譯成可驗收的形式：「專業一點」通常真正的意思是「不要用口語縮寫」或「每個主張都要有數據支撐」——問清楚或直接提出翻譯版本。

### 2. Objective ≠ Result —— 用「主詞測試」

**動作**：看這兩句話的主詞是誰。

- Objective 的主詞應該是**讀者或決策**：「讓主管在 2 分鐘內判斷進度是否在軌」「支撐下季預算配置的決定」
- Result 的主詞應該是**交付物**：「一份五段式 Markdown 週報」

如果 O 寫出來是「產出一封歡迎信」——主詞是交付物，那是 Result 被複製到 O 格了。這是最常見的失敗，尤其在分析類與文件類任務。

補救方法是追問一層：**「這份東西產出來之後，你要拿它去做什麼？」**答案就是真正的 Objective。

### 3. Character 有作用 —— 用「替換測試」

**動作**：把角色換成另一個合理的角色，想像產出會不會明顯不同。

- 「10 年經驗人資經理，擅長溫暖專業的溝通」→ 換成「法務主管」，整封信的語氣與取捨全變 ✓
- 「你是一位專業助理」→ 換成任何角色，產出都一樣 ✗

角色設定的重點不是頭銜，是**這個身分帶來的判斷傾向**。「習慣先講結論再講細節」「不把個人風格偏好當成阻擋理由」「從讀者第一次上手的視角組織內容，而不是從系統架構的視角」——這些才是真正在改變輸出的句子。

### 4. Situation 有資訊量 —— 用「刪除測試」

**動作**：把 Situation 整段刪掉，模型還能不能推出同樣的內容？

- 「我們是一家公司，需要寫信給員工」→ 刪掉毫無損失，這只是任務的複述 ✗
- 「30 人金融科技新創，文化扁平，新人第一週配一位 buddy」→ 刪掉之後 buddy 制度就寫不進信裡了 ✓

Situation 的功能是提供**外部事實**：規模、產業、時間點、既有制度、已發生的事、技術棧、讀者狀態。凡是模型可以從任務描述本身推得的，都不算資訊量。

### 5. Result 有骨架 —— 用「結構測試」

**動作**：只讀 Result 這一格，你能不能畫出成品的段落大綱？

- 「請寫一封 Email」→ 畫不出來 ✗
- 「Email 草稿，包含：開頭問候、報到日的三個小提醒、結尾一句鼓勵」→ 三段大綱清楚 ✓

進階一點的 Result 還會指定欄位格式，例如「每條格式為 `項目 — 負責人 — 狀態燈號 — 預計完成日`」。指定到欄位層級，模型就完全不需要猜結構。

### 6. 五維無矛盾 —— 用「相乘測試」

**動作**：把 R 的結構乘上 E 的限制，算算看合不合理。

最常見的衝突是**篇幅與結構打架**：E 限制 300 字，R 卻要求五個章節、每章都要有數據支撐。這種矛盾模型會自己選一邊犧牲，而且通常犧牲的不是使用者想留的那一邊。

發現衝突時不要默默調整，直接在自檢裡點出來並給兩個解法（放寬字數／簡化結構），讓使用者決定。

### 原則：誠實標記

**動作**：檢查自己的自檢是不是全部 ✅。這一條不列進輸出的自檢清單——它是寫前六條時要守的原則。

如果六項全通過而且沒有任何 ⚠️，先懷疑自己是不是在敷衍。實務上幾乎每份 prompt 都至少有一處值得標註——某個刻意留白、某個潛在張力、某個資訊仍然不足的地方。

⚠️ 有兩種正當用法：

- **真正的弱點**：「500 字上限與五段結構在專案較多時會擠壓，建議放寬到 800 字」
- **刻意的留白**：「沒有寫死專案名稱，這是為了保持模板泛用性；如果你們有固定產品線，補進情境段會更準」

第二種要註明「這是刻意的」，否則使用者會以為你漏了。

自檢的全部價值在於它會誠實指出弱點。一份全 ✅ 的自檢跟沒有自檢是一樣的。

## 各維度的反模式速查

| 維度 | 反模式 | 為什麼壞 |
|---|---|---|
| S | 「我們是一家公司」 | 任務複述，零資訊量 |
| S | 把五年公司沿革全寫進去 | 資訊量過載，稀釋了真正相關的事實 |
| C | 「你是一位專業的助理」 | 通不過替換測試 |
| C | 「你是世界頂尖的大師」 | 誇飾不會改變輸出，只會讓模型語氣浮誇 |
| O | 「產出一份報告」 | 主詞是交付物，這是 Result |
| O | 「做得又快又好」 | 沒有指向任何具體成效 |
| R | 「寫一封 Email」 | 沒有骨架，結構仍要猜 |
| R | 連字型與行距都指定 | 過度規格化，擠壓內容品質 |
| E | 「專業一點」「有深度」 | 通不過驗收測試 |
| E | 二十條限制 | 限制過多會互相衝突，模型只能挑著遵守 |

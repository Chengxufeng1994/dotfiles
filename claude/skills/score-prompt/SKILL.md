# SCORE 提示詞框架

## Why：為什麼模糊的 prompt 會失敗

「請幫我寫一封歡迎新進員工的信」這種指令不會失敗在 AI 不夠聰明，而是失敗在**它必須替使用者猜五件它猜不到的事**：公司是什麼樣子、該用誰的口吻、這封信真正要達成什麼、要什麼格式、有哪些不能踩的線。AI 猜錯任何一項，產出就得重寫。

SCORE 的價值是把這五個猜測點變成明確的輸入。每一維各自堵住一種缺口：

| 維度 | 堵住的缺口 | 缺了會怎樣 |
|---|---|---|
| **S**ituation 情境 | AI 不知道的外部背景 | 產出正確但不合身，像從網路範本抄來的 |
| **C**haracter 角色 | 用誰的專業與口吻說話 | 語氣飄移，時而官腔時而過度熱情 |
| **O**bjective 目標 | 這件事背後真正要達成什麼 | 形式做對了但沒解決問題 |
| **R**esult 產出 | 要哪種文件、什麼結構 | 格式要重講一次，來回消耗 |
| **E**xactness 限制 | 精確的邊界條件 | 長度、語氣、禁用詞全部要事後修 |

理解這層因果比背下五個字母重要。判斷某一維寫得好不好，唯一的標準是：**這句話有沒有讓 AI 少猜一件事？**

## 五個維度的判準

### S — Situation 情境
問的是：**這個任務發生在什麼環境裡？**

好的 Situation 提供 AI 不可能自行推得的外部事實：組織規模、文化、產業、時間點、已發生的前情。
- 好：「我們是一間 30 人的金融科技新創，文化扁平，強調快速試錯，新人第一週會配一位 buddy」
- 差：「我們是一家公司，需要寫信給員工」——這是把任務本身重講一遍，零資訊量

### C — Character 角色
問的是：**該把 AI 設成誰？**

角色設定要具體到能改變輸出。判斷方法：把角色換掉，產出會不一樣嗎？不會的話這個角色就是裝飾。
- 好：「你是一位 10 年經驗的人資經理，擅長溫暖又專業的溝通，寫過上百封新人信」
- 差：「你是一位專業助理」——換成任何角色結果都一樣

### O — Objective 目標
問的是：**為什麼要做這件事？成功長什麼樣子？**

這是最常被寫壞的一維，因為很容易寫成 Result 的複述。分辨方法：**Objective 講「讀者看完之後會怎樣」，Result 講「我手上會拿到什麼」**。
- 好：「讓新人在報到前就降低焦慮，知道第一週要做什麼，並感覺到公司在期待他」
- 差：「產出一封歡迎信」——這是 Result，不是 Objective

### R — Result 產出
問的是：**要哪一種文件、什麼結構？**

只講文件類型不夠，要講骨架。
- 好：「請產出 Email 草稿，包含：開頭問候、報到日的三個小提醒、結尾一句鼓勵」
- 差：「請寫一封 Email」——結構仍要 AI 猜

### E — Exactness 限制
問的是：**有哪些精確的邊界？**

判準是**可驗證性**：拿到成品後能不能客觀判斷有沒有做到。
- 好：「300 字以內，語氣輕快幽默，不使用『敬啟者』『台端』等生硬官方詞彙」
- 差：「寫好一點、專業一點」——無法驗證，等於沒寫

## 工作流程

### Step 1：先自己做一版推測，不要空手發問

讀完使用者的原始需求後，先在心裡把五維各填一個最合理的猜測。這一步不輸出給使用者看，但決定了問答品質——**有草案才問得出好問題**。

例如收到「請幫我寫一封歡迎新進員工的信」，推測：
- S：不明（這是真的缺口，必須問）
- C：人資或直屬主管（需要使用者選）
- O：降低報到焦慮 / 傳達文化 / 交代待辦（三者權重不同，需要選）
- R：Email，含問候＋事項＋結尾（可推測，請使用者確認）
- E：不明（長度、語氣需要問）

### Step 2：用選項式問答補齊，分兩輪

用 `AskUserQuestion` 提問。第一輪問 S / C / O（決定內容的靈魂），第二輪問 R / E（決定外觀，且合理選項受第一輪答案影響）。五維拆成兩次對話，資訊完整度不變但摩擦大幅降低——五輪會讓人第二次就不想用了。

三個核心原則：**選項是候選答案而非問題分類**（使用者點下去那一維就填好了，不必再打字）；**三個選項代表三種真正不同的方向**（各寫一次成品會明顯不同）；**第一個選項是你的推薦並標註「（推薦）」**。

每題的 header 用維度的中文名稱（情境 / 角色 / 目標 / 產出格式 / 限制條件），讓使用者看得出自己在五維的哪個位置。

使用者原始需求裡已經明確的東西，仍然出一題，但把他的原話填成推薦選項——一律先問答的價值不在盤問，在**給確認機會**。

寫問答前讀 `rules/question-design.md`，裡面有好／壞選項的具體對照與分輪的完整理由。

### Step 3：輸出雙區塊

確認完成後，用這個結構輸出：

```markdown
## SCORE 拆解
（五維表格，給人看，讓使用者一眼掃出哪一維薄弱）

## 成品 Prompt
（放進 code fence，給模型看，使用者一鍵複製帶走）

## 自檢
（逐項結果）
```

拆解表與成品 prompt 的讀者不同，因此寫法必須不同——最常見的錯誤是把表格內容原封貼進 code fence，那對模型是條列雜訊而不是指令。成品 prompt 要用有語意的中文小標（「情境」「你的角色」「任務目標」「輸出要求」「限制條件」）而非 S/C/O/R/E 字母代號，用第二人稱直述句，並把表格的濃縮語展開舉例。

如果使用者要的是會反覆使用的東西（週報、review、每次都要跑一遍的流程），成品 prompt 還要做**變數槽**：固定的五維寫死，每次會變的素材留一個明確的輸入區。

寫輸出前讀 `templates/deliverable-structure.md`（可直接套用的骨架與兩種寫法的對照）；若是可重用模板，再讀 `templates/reusable-prompt.md`。

### Step 4：自檢

輸出前逐項檢查，把結果列在最後。這一步存在的理由是：**寫壞的 prompt 通常不是漏了某一維，而是某一維寫了但沒有作用**，而這種空轉從表面看不出來。

| 檢查項 | 判斷動作 |
|---|---|
| Exactness 可驗證 | 驗收測試：假裝成品交來了，每條限制能不能打勾或打叉？ |
| Objective ≠ Result | 主詞測試：O 的主詞是讀者或決策，R 的主詞是交付物 |
| Character 有作用 | 替換測試：換一個合理角色，產出會不會明顯不同？ |
| Situation 有資訊量 | 刪除測試：整段刪掉，模型還能不能推出同樣內容？ |
| Result 有骨架 | 結構測試：只看這格，能不能畫出成品的段落大綱？ |
| 五維無矛盾 | 相乘測試：R 的結構乘上 E 的限制，合不合理？ |

通過標 ✅，有疑慮標 ⚠️ 並用一句話說明怎麼補。

第七條是寫這六條時要守的原則，不另外列一行：**誠實標記**。不要為了好看而全部給 ✅——自檢的全部價值在於它會誠實指出弱點；一份全 ✅ 的自檢跟沒有自檢是一樣的。六項全過而且找不到任何值得標 ⚠️ 的地方時，先懷疑自己在敷衍。如果某處是使用者主動選擇留白，標 ⚠️ 但註明「這是刻意的」，否則他會以為你漏了。

每項判斷動作的操作細節與各維度的反模式速查，見 `rules/quality-check.md`。

## 邊界情況

**使用者貼來一段既有 prompt 要優化**：先逆向拆解，把現有內容對應到五維，明確指出哪幾維是空的或無效的，再針對空缺提問。不要從零重寫——他既有的內容通常藏著他沒說出口的需求。

**需求本身已經很完整**：仍走一輪確認，但把所有選項預填成他的原話。這時的價值不在補資訊，而在讓他看見自己的需求被拆成五維後哪裡其實還是空的。

**要產出英文或其他語言的 prompt**：拆解表與自檢用繁體中文，成品 prompt 用目標語言。

**任務是技術性的**（寫程式、系統設計、code review）：五維的語意會整體移位——Character 變成審查視角，Situation 是技術棧與 CI 涵蓋範圍，Exactness 是可編譯、有行號、有分級。框架照用，但選項要換成技術脈絡的候選值，細節見 `references/code-review.md`。

## 資料夾結構

```
score-prompt/
├── SKILL.md      # 你正在讀的這份：五維判準 + 四步流程
├── rules/        # 「該遵守什麼？」——判準與檢核
├── templates/    # 「成品長什麼樣？」——輸出格式樣板
└── references/   # 「這類任務長什麼樣？」——七個已完成的範例
```

每個檔案是一個獨立概念，按需讀取，不必全部載入。典型一次任務會讀四到五個檔案：兩個 rules、一到兩個 templates、一個 references。

### rules/ — 做每個 Step 之前讀對應的那份

| 檔案 | 什麼時候讀 |
|---|---|
| `rules/question-design.md` | 準備 Step 2 的問答。好／壞選項的對照、三個條件、分輪邏輯、使用者喊停時怎麼辦 |
| `rules/quality-check.md` | 執行 Step 4 的自檢。六項判斷動作的操作方式、誠實標記原則、⚠️ 的兩種正當用法、各維度反模式速查 |

### templates/ — 寫 Step 3 的輸出時讀

| 檔案 | 什麼時候讀 |
|---|---|
| `templates/deliverable-structure.md` | 每次都讀。可直接套用的骨架、拆解表與成品 prompt 的寫法對照 |
| `templates/reusable-prompt.md` | 產出是會反覆使用的模板時才讀。Situation 兩層拆分、變數槽的兩種寫法、收尾的使用建議 |

### references/ — 依任務性質讀最接近的一份

每份都有該類任務的五維重心、問答選項設計要點、一個完整範例與常見陷阱。

**這些是範例不是模板。**讀它們是為了看出**選項該沿哪條軸拉開**、**哪一維在這類任務裡最容易寫壞**，而不是把裡面的 SCORE 內容搬到使用者的產出裡。同樣是週報，五人產品團隊和三十人事業部要問的選項完全不同——照抄範例的內容，等於跳過了整個問答的意義。

| 檔案 | 適用任務 |
|---|---|
| `references/business-writing.md` | 信件、公告、客訴回覆、對外文案、內部通知 |
| `references/status-report.md` | 週報、月報、專案狀態更新、跨部門同步、向主管的請求 |
| `references/client-proposal.md` | 顧問提案、報價單、企劃書、內部立案、募資簡報 |
| `references/literature-review.md` | 文獻回顧、競品比較、市場調查綜整、多來源資料整理 |
| `references/data-analysis.md` | 銷售分析、營運報表、A/B 測試解讀、決策支援 |
| `references/technical-docs.md` | API 文件、README、架構說明、runbook、上手指南 |
| `references/code-review.md` | PR review、重構建議、架構評估、技術選型 |

有兩組容易混淆，挑錯會導致選項軸拉錯方向：

- **書信 vs 進度回報**：書信要引起感受，進度回報要引起判斷或行動。週報、狀態更新一律走 `references/status-report.md`
- **文獻綜整 vs 資料分析**：綜整要**克制判斷**（把來源排整齊讓使用者自己看出結論），分析要**下判斷**（支撐某個決策）。使用者說「整理」「比較」「有沒有共識」走綜整，說「分析」「為什麼」「該怎麼辦」走分析

任務不在七個情境裡時，挑最接近的一份參考它的**分化邏輯**（選項該沿哪條軸拉開），而不是照抄它的內容。

# 模板：交付結構

Step 3 的輸出骨架，以及拆解表與成品 prompt 為什麼必須用不同寫法。

## 可直接套用的骨架

外層用四個反引號，因為骨架裡面本身就含有一層三反引號的 code fence。成品 prompt 若本身又含 fence（例如技術類任務要示範程式碼格式），外層再往上加一個反引號。

````markdown
## SCORE 拆解

| 維度 | 內容 |
|---|---|
| **S** 情境 | … |
| **C** 角色 | … |
| **O** 目標 | … |
| **R** 產出 | … |
| **E** 限制 | … |

## 成品 Prompt

（一句話說明怎麼用：整段複製、哪裡要換）

```
## 情境
…

## 你的角色
…

## 任務目標
…

## 輸出要求
…

## 限制條件
- …
```

## 自檢

- ✅ **Exactness 可驗證**：…
- ✅ **Objective ≠ Result**：…
- ✅ **Character 有作用**：…
- ✅ **Situation 有資訊量**：…
- ✅ **Result 有骨架**：…
- ⚠️ **五維無矛盾**：…
````

自檢的六條對應 `rules/quality-check.md` 的六項檢查；第七條「誠實標記」是寫這六條時要守的原則，不另外列一行。

## 為什麼兩個區塊寫法不同

它們的讀者不同。最常見的錯誤是把表格內容原封貼進 code fence——那對模型是條列雜訊，不是指令。

### 拆解表：寫給人看

**用途**：讓使用者一眼掃出哪一維薄弱、想改哪裡改哪裡。

**寫法**：極度濃縮，每格一到兩句。用 `**S** 情境` 這種字母加中文的標示，因為字母在表格裡是最快的定位錨點。

**判準**：使用者看完這張表，能不能在三秒內指出「我想改 O 那一格」？

### 成品 Prompt：寫給模型看

**用途**：使用者複製出去、貼到別的對話裡直接用的東西。

**四個原則**：

**一、用有語意的中文小標，不要用字母代號。**「情境」「你的角色」「任務目標」「輸出要求」「限制條件」——這些詞本身就攜帶指令意義。而 `S:` `C:` `O:` 對模型只是字母，多一層解碼成本卻沒有任何好處。字母代號是給人定位用的，留在拆解表就好。

**二、用第二人稱直述句，像在交代一位新來的同事。**「你是一位有 10 年經驗的人資經理」比「角色：人資經理」有效，因為前者建立了身分認同，後者只是貼標籤。

**三、展開，不要沿用表格的濃縮語。**拆解表寫「不用生硬官方詞彙」，成品 prompt 要寫「不使用『敬啟者』『台端』『特此通知』等生硬的官方詞彙」。把抽象的限制舉例化，模型才知道界線在哪。

**四、一定要放在 code fence 裡。**這是使用者要一鍵複製的成品。放在 fence 外面等於逼他手動框選，體驗差一截。

## 對照範例

同一個維度，兩種寫法：

| | 拆解表 | 成品 Prompt |
|---|---|---|
| **C** | 10 年經驗人資經理，擅長溫暖又專業的溝通 | 你是一位有 10 年經驗的人資經理，擅長溫暖又專業的溝通，寫過上百封新人歡迎信。你知道新人在報到前最在意的其實不是制度，而是「我會不會格格不入」。 |
| **E** | 300 字以內，語氣輕快幽默，不用生硬官方詞彙 | ‑ 全文 300 字以內<br>‑ 語氣輕快、帶點幽默，像同事在講話<br>‑ 不使用「敬啟者」「台端」「特此通知」等生硬的官方詞彙 |

左欄用來掃讀與定位，右欄用來執行。內容相同，密度與具體度完全不同。

## 如果這是會反覆使用的東西

週報、PR review、客訴回覆、每次都要跑一遍的流程——成品 prompt 還要加上變數槽與使用建議，見 `templates/reusable-prompt.md`。

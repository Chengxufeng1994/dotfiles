# 模板：可重複使用的 Prompt

當使用者要的不是一次性產出，而是**每週／每次都會跑一遍的東西**，成品 prompt 要多做兩件事：變數槽，以及使用建議。

## 什麼時候要做

使用者說了「可重複使用」「模板」「每週」「每次」「以後都用這個」，或任務本身明顯會反覆發生（週報、PR review、客訴回覆、會議記錄總結、面試回饋）。

一次性任務不需要，多做只是雜訊。

## 核心動作：把 Situation 拆成兩層

這是最容易做錯的一步。使用者描述情境時，會把**穩定事實**和**本期素材**混在一起講：

> 我帶五人產品團隊，本週 A 案完成 80%、B 案資源不足、C 案還沒開始

「帶五人產品團隊」是穩定的，每週都一樣；「A 案 80%」是本週的，下週就變了。寫死在 Situation 裡，等於每週都要改 prompt 的上半部——模板的價值消失一半。

正確做法：S / C / O / R / E 五段寫死，本期素材放到底部的變數槽。

## 變數槽的兩種寫法

### 單一輸入區

適合素材形式不固定、一次貼一大塊的情況：

```
## 本週原始素材
（把這週的站會筆記、Jira 匯出、Slack 討論、成員回報全部貼在這裡，格式凌亂沒關係）

<<<
[貼上本週素材]
>>>
```

### 多欄位佔位符

適合每次的輸入有固定幾個部分：

````
**PR 標題**：{{PR 標題}}

**PR 描述／解決的問題**：
{{作者寫的 description，或一句話說明這個 PR 想解決什麼}}

**相關背景**（可留白）：
{{例如：這段程式碼會被 X 服務高頻呼叫／這是為了修 #123 的線上事故}}

**變更內容（diff）**：
```diff
{{在此貼上 git diff}}
```
````

注意這裡的外層用四個反引號——因為佔位符區塊內部含有 ```diff 這一層 fence。輸出給使用者的成品 prompt 只要內含任何 code fence，外層就必須加一級，否則 fence 會提早閉合，使用者複製到的東西會是斷的。

## 三個關鍵細節

**一、在 code fence 上方用一句話說明哪裡要換。**「整段複製即可重複使用，每次只要替換最下方『本次 PR 資訊』區塊」——少了這句，使用者得自己讀完整段才知道邊界在哪。

**二、在輸入區的說明裡主動放寬格式要求。**「格式凌亂沒關係」「可留白」——模板的價值就在降低每次使用的準備成本。如果每次都要先整理素材，那就不叫模板了。

**三、佔位符裡放例子而不只是欄位名。**`{{相關背景}}` 使用者不知道該寫什麼；`{{例如：這段程式碼會被 X 服務高頻呼叫／作者是剛加入的新人}}` 他一看就懂這欄的用途與粒度。

## 收尾的使用建議

雙區塊與自檢之後，加三到四句「使用建議」，回答使用者拿到成品後最可能有的疑問：

- **第一次用要先改哪裡**——通常是情境段，因為它的資訊量直接決定產出品質，而且這是一次性投資
- **之後每次只需要換什麼**——指向變數槽
- **產出總是差一點時該往哪一維補**——例如「如果你每次都在改同一個地方，就把那條修正寫進限制條件」

這段的價值在於**把一次性的交付變成可演進的資產**。使用者用滿一個月後如果總在改同一個地方，那就是某一維寫得不夠，他應該知道去哪裡補。

一次性的簡單任務可以省略這段，別為了格式完整而硬寫。

## 完整範例

`references/code-review.md` 的成品 prompt 是這個模式最完整的示範：五維寫死、底部四個 `{{ }}` 佔位符、fence 上方一句使用說明、結尾四點使用建議。`references/status-report.md` 則示範了 Situation 兩層拆分沒做好時，自檢會怎麼把它標出來。

# 事故文件模板

語言跟著團隊走。事故溝通的讀者是同事與使用者，用他們最快讀懂的語言——這比格式一致重要。

## 時間軸（步驟一就開始寫）

不是給人看的文件，是給你自己的暫存區。醜沒關係，**有時間戳就好**。

```
14:02 收到 api_5xx_rate 告警
14:03 確認 dashboard，5xx 從 0.1% 跳到 34%
14:05 檢查最近部署：14:00 上了 v2.31.0
14:06 決定回滾
14:09 回滾完成，開始觀察
14:14 5xx 回到 0.2%
14:30 持續正常，標記 Resolved
```

每個動作一行。**做了什麼、看到什麼、決定什麼**都要記，尤其是「決定」——postmortem 最需要的是當時為什麼那樣判斷。

## 狀態更新

```markdown
## Incident Update: [一句話標題]

**Severity:** SEV[1-4] | **Status:** Investigating | Identified | Mitigating | Monitoring | Resolved
**Impact:** [誰受影響、受什麼影響]
**Updated:** [UTC 時間]

### 現況
[目前確認的事實。不要寫推測]

### 已採取的動作
- [動作與時間]

### 下一步
- [接下來要做什麼，以及下次更新時間]
```

四個必答：**現在怎樣、誰受影響、我們在做什麼、下次更新什麼時候**。少任何一項，讀的人就會來私訊問你，而回答那些訊息會拖慢處理。

`Status` 的五個值不要跳過 `Mitigating`——它告訴讀者「已經知道怎麼止血、正在做」，跟 `Identified`（知道原因但還沒動作）是不同的訊號。

### 對外溝通

給使用者的版本更短，而且**不要出現內部術語**：

```markdown
[產品名] 目前有部分使用者無法完成結帳。我們已找到原因並正在修復，
預計 30 分鐘內恢復。下次更新時間：15:00。
```

不寫技術細節、不寫哪個服務、不解釋架構。使用者要知道的只有三件事：**是不是我的問題、有多嚴重、什麼時候好**。

## Postmortem

```markdown
# Postmortem: [標題]

**日期:** [日期] | **持續:** [X 小時 Y 分] | **等級:** SEV[X]
**撰寫:** [誰] | **狀態:** Draft | Reviewed

## 摘要

[2-3 句白話。假設讀者不熟這個系統]

## 影響

- [多少使用者、哪些功能、多長時間]
- [可量化的業務影響，有的話]

## 時間軸

| 時間 (UTC) | 事件 |
|---|---|
| 14:02 | 收到告警 |
| 14:06 | 決定回滾 |
| 14:14 | 指標恢復 |

## 根因

[發生了什麼，以及為什麼系統允許它發生]

## 5 Whys

1. 為什麼 [症狀]？ → [因為…]
2. 為什麼 [上一層]？ → [因為…]
3. …
4. …
5. … → [根因]

## 哪裡做對了

- [真的有效的部分——這一節不是客套，它決定哪些機制值得保留與複製]

## 哪裡做得不好

- [對系統與流程，不對人]

## 行動項

| 行動 | 負責人 | 優先序 | 期限 |
|---|---|---|---|
| [具體到可以判斷有沒有做完] | [人名] | P0/P1/P2 | [日期] |

## 學到什麼

[給沒參與這次事故的人看的一段。什麼樣的判斷以後可以複用]
```

### 三個容易寫壞的地方

**摘要寫成技術報告。** 摘要的讀者是沒參與的人——主管、其他團隊、三個月後的自己。用白話寫「什麼壞了、多久、為什麼」，技術細節留給根因那節。

**「哪裡做對了」被當成客套省略。** 它其實有實際功能：找出哪些機制真的有效，值得保留與複製到別處。告警在兩分鐘內響了、回滾程序三分鐘跑完——這些是投資回報的證據。

**行動項寫成願望。** 「改善監控」不是行動項，「為 payment 服務的 p99 延遲加告警，門檻 2 秒」才是。判準：**看得出有沒有做完嗎？**

## 記錄放哪

事故文件建議進版本庫（`docs/incidents/YYYY-MM-DD-短標題.md`），理由跟 ADR 一樣：**它是決策紀錄，而不是一次性的溝通**。放在聊天軟體裡的 postmortem，半年後沒有人找得到。

# 止血優先，以及 blameless 實際怎麼做

## 為什麼診斷的本能在事故當下是錯的

平常先理解再動手是對的——改錯地方會製造新問題。但事故當下的計價方式不同：**你思考的每一分鐘都在向使用者收費**，而多數止血手段（回滾、關 flag、重啟）是可逆的，做錯了損失很小。

風險不對稱時，行動的門檻應該降低。這不是叫你亂試，是叫你**先用便宜且可逆的動作換時間，再用那段時間好好診斷**。

## 止血手段，依序試

### 1. 回滾

最近有部署嗎？先滾回去。

「但可能不是這次部署造成的」**不是不滾的理由**。回滾是可逆的、幾分鐘的、而且會直接排除掉最大的一類嫌疑。繼續查不是可逆的——花掉的時間拿不回來。

滾完症狀還在，你就免費得到一個結論：不是那次部署。

### 2. 關掉

有 feature flag 就關掉。沒有的話問：能不能停用那條路徑、擋掉那個 endpoint、把流量導開？

**「關掉壞的功能」通常比「修好壞的功能」快兩個數量級。**

### 3. 擴容或重啟

資源耗盡（連線數、記憶體、磁碟）或程序狀態壞掉時最有效。

重啟的壞名聲來自「重啟就好了然後不查原因」——但事故當下重啟是止血，查原因是 postmortem 的事。**兩者不衝突，只是順序。**

### 4. 降級

關掉次要功能保住核心。推薦欄壞掉導致首頁整頁失敗時，讓推薦欄回傳空陣列，首頁就活了。

## 什麼時候該診斷而不是止血

三種情況：

- **四種止血手段都不適用**（沒部署、沒 flag、不是資源問題、沒有可降級的部分）
- **止血動作本身有風險**（回滾會導致資料格式不相容、需要跑反向 migration）
- **資安事故**——保全證據優先。這是唯一一個「先別動」正確的情況，因為止血動作會破壞入侵路徑的痕跡

進診斷模式時，設一個時間盒（SEV1 給 15 分鐘），時間到了還沒結論就回頭重新評估止血選項。**隧道視野是獨自處理事故最大的風險**，時間盒是唯一可靠的解法。

## 需要證據又要止血時

先抓快照再動手，順序是：

```bash
# 30 秒內能做完的取證
kubectl logs <pod> --tail=1000 > /tmp/incident-logs.txt
# 存下當前 metrics 圖表截圖 / 匯出
# 記下當前的部署版本、設定值、feature flag 狀態
```

抓完就止血。**不要為了「完整取證」讓使用者繼續痛**——不完整的證據加上恢復的服務，勝過完整的證據加上持續的停機。

## Blameless postmortem 實際怎麼寫

「blameless」不是不寫發生了什麼，是**把因果指向系統而不是人**。

判斷方法：每寫一句話，問「如果換一個人在同樣的處境，會不會也做出同樣的事？」會的話，那就是系統問題。

| 指向人（差） | 指向系統（好） |
| --- | --- |
| 某人推了錯的設定 | 設定變更不需 review 就能直接生效於 production |
| 值班的人沒注意到告警 | 該告警與其他 40 個低優先告警混在同一個頻道 |
| 開發時忘記加測試 | 這條路徑沒有測試也能通過 CI |
| 某人回滾太慢 | 回滾程序寫在一份需要三次點擊才找得到的 wiki |

右欄的共同點是**它們都可以被修**。左欄不行——「請大家更小心」不是行動項。

### 5 Whys 用得對

每一層要回答「為什麼上一層會發生」，而不是換句話說。

```
為什麼結帳失敗？        → 支付服務回 500
為什麼支付服務回 500？  → 資料庫連線池耗盡
為什麼連線池耗盡？      → 一個新查詢沒有用 context timeout，慢查詢累積
為什麼沒有 timeout？    → 沒有 lint 規則檢查，review 也沒有這一項
為什麼沒有那個檢查？    → 這類問題以前沒發生過，沒人想到要加
```

**停在第三層是最常見的錯誤**——那裡通常還是技術症狀，不是根因。第四、第五層才會碰到流程與制度，而那正是能被修的地方。

### 行動項

每一項都要有負責人與期限，否則它只是讓 postmortem 看起來完整。

寧可寫三個真的會做的，也不要寫十個許願的。**沒有人做的行動項會侵蝕 postmortem 的可信度**——下一次就沒有人認真對待它了。

如果某個問題確實不打算修，明寫「接受這個風險，因為 X」。這比讓它躺在清單裡假裝會被處理誠實得多。

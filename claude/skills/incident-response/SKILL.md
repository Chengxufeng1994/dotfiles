# Incident Response

事故當下最難的判斷不是分級，是**什麼時候停止診斷、改成止血**。

工程師的本能是先理解再動手。平常這是美德，事故當下它是在用**使用者的停機時間**換自己的好奇心。理解可以等到 postmortem，使用者不能等。所以這份流程的核心是一條優先序：**先讓它不痛，再搞懂它為什麼痛。**

第二個容易搞砸的是時間軸——postmortem 難產幾乎都是因為當下沒人記時間戳，事後靠回憶重建。所以開時間軸是第一步，不是最後一步。

## 使用時機

- 線上出事，要決定嚴重程度與該做什麼
- 收到 alert，不確定要不要當成事故處理
- 事故進行中，要對內或對外發狀態更新
- 事故結束，要寫 postmortem
- 想判斷某件事算不算事故

## Skill Boundaries

- 事故已經止血，要找出程式碼層級的根因 → 改用 `debugging-and-error-recovery`（事故當下不要走那套，太慢）
- 要**預防**事故：加監控、加告警、加 SLO → 改用 `observability-and-instrumentation`
- 要改上線流程避免重蹈覆轍 → 改用 `deployment-patterns` 或 `ci-cd-and-automation`
- postmortem 產出的架構決策要留紀錄 → 改用 `architecture-decision-records`
- 本 SKILL 管 **從發現到 postmortem 的事故處理本身**：分級、溝通、止血、檢討

## 流程

### 步驟一：開時間軸，然後才做別的

```bash
# 開一個檔案，之後每個動作都往裡面加一行
echo "$(date -u +%H:%M) 事故開始記錄" >> incident-$(date +%Y%m%d).md
```

**每做一件事就記一行，附 UTC 時間。** 包含：什麼時候發現的、看了哪個儀表板、改了什麼設定、什麼時候恢復的。

這一步值三十秒，但它決定 postmortem 寫得出來還是靠回憶編。事故當下沒有人記得住順序，而順序正是事後最需要的東西。

### 步驟二：分級

| 等級 | 判準 | 反應 |
| --- | --- | --- |
| **SEV1** | 服務不可用，全部或多數使用者受影響；或有資料遺失風險 | 立刻，找人一起 |
| **SEV2** | 主要功能降級，相當比例的使用者受影響 | 15 分鐘內 |
| **SEV3** | 次要功能有問題，少數使用者受影響 | 一小時內 |
| **SEV4** | 外觀問題或影響極小 | 下個工作日 |

**不確定時往高報。** 降級很便宜，升級很貴——SEV3 拖成 SEV1 的過程中，沒有人在處理它。

分級看**使用者受到的影響**，不看技術上有多嚴重。資料庫主節點掛掉但自動切換成功、使用者無感 → 不是 SEV1（但要記錄）。一個結帳按鈕壞掉 → 可能是 SEV1。

### 步驟三：止血，不要診斷

**先問「有沒有辦法讓它現在不痛」，而不是「為什麼會這樣」。**

依序試最便宜的止血手段：

1. **回滾**——最近有部署嗎？先滾回去。「但可能不是這次部署造成的」不是不滾的理由，滾回去是可逆的，繼續查不是
2. **關掉**——有 feature flag 就關掉；沒有的話能不能停用那條路徑
3. **擴容／重啟**——資源耗盡或狀態壞掉時最快
4. **降級**——關掉次要功能保住主要功能

四種都不行才進診斷，判準與例外見 `rules/mitigate-first.md`。

止血成功之後**事故還沒結束**——狀態變成 Monitoring，繼續觀察到確認穩定。

### 步驟四：溝通

固定節奏發更新，即使沒有進展也要發——**沉默會讓別人來問你，而回答那些問題會拖慢處理**。

- SEV1：每 30 分鐘
- SEV2：每小時
- SEV3 以下：有進展時

每則更新回答四件事：現在怎樣、誰受影響、我們在做什麼、下次更新是什麼時候。模板見 `templates/incident-docs.md`。

**只寫已知事實，不寫推測。** 事故中的推測會被當成結論轉傳，然後你要花時間收回它。

### 步驟五：確認結束

同時滿足才算結束：症狀消失、指標回到正常區間、而且**你知道為什麼它現在是好的**。

最後一項容易被跳過。不知道為什麼好了，就不知道它會不會再壞——那應該維持 Monitoring 而不是 Resolved。

### 步驟六：寫 postmortem

SEV1、SEV2 一定要寫；SEV3 以下看有沒有值得記的教訓。

用 `templates/incident-docs.md` 的骨架。核心是 5 Whys 與行動項，寫法與 blameless 的實際做法見 `rules/mitigate-first.md` 的最後一節。

**趁記憶還熱的時候寫**，最好 48 小時內。時間軸已經在步驟一累積好了，這時只是補上因果。

## 規則

- IMPORTANT：**先開時間軸再做任何事。** 三十秒的成本，換 postmortem 寫得出來。事後重建的時間軸幾乎都是錯的。
- IMPORTANT：**止血優先於診斷。** 事故當下的目標是讓使用者不痛，不是搞懂原因。理解留給 postmortem。
- IMPORTANT：**不確定分級時往高報。** 降級便宜，升級貴——低報的那段時間沒有人在處理它。
- IMPORTANT：**分級看使用者影響，不看技術嚴重度。**
- IMPORTANT：**固定節奏發更新，沒進展也要發。** 沉默會招來詢問，而回答詢問會拖慢處理。
- NEVER：**事故中不可寫推測。** 只寫已知事實與已採取的動作。推測會被當結論轉傳，之後要花更多力氣收回。
- NEVER：**不可為了保留現場而不止血。** 需要證據就先抓快照（log、dump、metrics 截圖）再回滾，不要為了取證讓使用者繼續痛。
- NEVER：**postmortem 不可指向個人。** 「某人推錯了設定」要寫成「設定變更沒有經過 review 就能生效」。人會犯錯是常數，系統允許那個錯誤造成傷害才是變因。
- NEVER：**行動項不可沒有負責人與期限。** 沒有主人的行動項等於沒有——它只是讓 postmortem 看起來完整。

### 邊界情況

- **不確定算不算事故** → 用使用者影響判斷：有人正在受影響嗎？沒有就記錄下來走一般流程，不要啟動事故程序
- **止血了但不知道為什麼好了** → 維持 Monitoring，不要標 Resolved。並在 postmortem 裡誠實寫「根因未確認」而不是編一個
- **事故牽涉資安（資料外洩、未授權存取）** → 一律 SEV1，而且**先保全證據再止血**，這是本 SKILL 唯一不適用「止血優先」的情況
- **一個人處理** → 每 15 分鐘停下來看一次時間軸，強迫自己跳出隧道視野。獨自處理最大的風險是在一條錯的路上鑽太久
- **事故已經結束很久才要補 postmortem** → 照寫，但在開頭標明是事後補寫、時間軸靠回憶重建，讓讀者知道精確度有限

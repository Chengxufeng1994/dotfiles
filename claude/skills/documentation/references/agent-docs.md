# 寫給 AI agent 讀的文件

`CLAUDE.md`、`AGENTS.md`、`.cursorrules` 這類檔案。

## 跟人類文件的根本差異

**人類把文件當參考，agent 把文件當指令。**

寫錯的人類文件會被忽略——讀的人覺得不對就去看程式碼了。寫錯的 agent 文件會**被照做**，而且每一次都照做。這個差異推出三個具體後果：

1. **模糊的句子有害而不只是無用。** 「盡量寫測試」會被詮釋成任何東西；「新功能要有測試才能提交」是可執行的
2. **每一條都有成本。** 這些檔案每次對話都進 context。寫十條沒人在乎的規則，會稀釋掉那三條真正重要的
3. **過期的規則會主動造成錯誤。** 人類看到「用 npm」但專案已經改用 pnpm 會自己判斷；agent 會跑 `npm install`

## 該寫什麼

| 內容 | 為什麼 agent 需要 |
| --- | --- |
| **怎麼跑測試／建置／lint** | 猜不出來，猜錯就浪費一整輪 |
| **專案結構的非顯而易見處** | 「`internal/` 底下依 DDD 分層，不要在 handler 放商業邏輯」 |
| **這個 repo 的慣例與偏好** | 命名、錯誤處理方式、用哪個套件而不用哪個 |
| **禁止事項與其理由** | 「不要動 `generated/`，它由 `make gen` 產生」 |
| **陷阱** | 「跑 `make dev` 前要先 `docker compose up`，否則會出現看不懂的連線錯誤」 |

## 不該寫什麼

- **通用的好習慣**（「寫乾淨的程式碼」「注意效能」）。模型本來就會，寫了只是佔 context
- **能從檔案推得出來的**（技術棧、依賴版本、目錄清單）——agent 讀得到 `package.json` 和 `ls`
- **長篇的架構說明**。放在 `docs/` 並在這裡連結；`CLAUDE.md` 是索引不是知識庫
- **一次性的指示**。那屬於對話，不屬於檔案

## 寫法

**用祈使句，可驗證。**

| 差 | 好 |
| --- | --- |
| 「要注意錯誤處理」 | 「錯誤一律用 `fmt.Errorf("...: %w", err)` 包裝後回傳，不要 `log.Fatal`」 |
| 「盡量保持函式簡短」 | 「函式超過 50 行時拆開」 |
| 「使用適當的測試」 | 「新增的 exported 函式要有 table-driven 測試」 |

判準：**這條規則有沒有被遵守，能不能客觀看出來？** 看不出來的話，agent 也不知道自己有沒有做到。

**解釋為什麼，尤其是反直覺的規則。** 「不要用 `context.Background()`，一律往下傳 caller 的 context，否則取消訊號會斷在這裡」——理由讓 agent 能在你沒預料到的情境正確類推。只給規則不給理由，遇到邊界情況它只能猜。

## 篇幅

**短。** 每一行都在跟其他行競爭注意力，也在花掉每一次對話的 context。

實務上的判斷：**這一條如果拿掉，agent 會做錯事嗎？** 不會就拿掉。定期回頭刪掉沒在作用的規則，比不斷新增有價值。

需要長篇內容時，在 `CLAUDE.md` 放一行指向 `docs/` 的連結，並寫明什麼時候該去讀——這樣它只在需要時才進 context。

## 維護

專案的慣例改了，這個檔案要跟著改，而且**優先序比一般文件高**：一般文件過期會誤導偶爾讀它的人，這個檔案過期會誤導每一次對話。

改了建置指令、換了套件管理器、搬了目錄之後，順手檢查一次這個檔案。

## 一個常見錯誤

把 `CLAUDE.md` 寫成給人看的專案介紹。它的讀者不需要知道專案願景或功能列表——它需要知道**在這個 repo 裡怎麼正確地動手**。專案介紹放 README，兩者的讀者與用途都不同。

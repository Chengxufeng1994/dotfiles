# Documentation

文件唯一持久的價值，是**程式碼說不出來的東西**。程式碼已經說了 what；文件要說的是 why、給誰、什麼時候用、什麼情況會壞。

其他內容都會腐爛——程式碼會變，散文不會跟著變。而過期文件不是「沒價值」，是**主動誤導**：讀的人會相信它，然後照著做錯的事。所以寫文件的第一個問題不是「要寫什麼」，是**「什麼會讓這段變錯，而且沒人會發現」**。

## 使用時機

- 要寫 README、API 文件、runbook、架構說明、上手指南
- 在猶豫某段程式碼該不該加註解
- 要寫或修 `CLAUDE.md` / `AGENTS.md` 這類給 AI agent 讀的文件
- 既有文件過期了，要判斷該改、該刪、還是該換一種形式
- 有人反覆問同一個問題，想把答案寫下來

## Skill Boundaries

- 架構**決策**的紀錄（為什麼選這個技術、否決了什麼）→ 改用 `architecture-decision-records`
- 功能規格與實作計畫 → 改用 `writing-a-spec` / `writing-a-plan`
- 對**某段程式碼**做口頭講解、幫人理解 → 改用 `explain-code`（那是即時解釋，不是留下來的文件）
- API 的**設計**（資源怎麼切、版本策略）→ 改用 `api-and-interface-design`；本 SKILL 只管把設計好的東西寫清楚
- 提交訊息與 PR 描述 → 改用 `commit-message` / `create-pull-request`
- 本 SKILL 管 **會被留下來、之後會被別人讀的說明文字**，從一行註解到一整份上手指南

## 前置確認（Ask User）

使用者沒講清楚時，開始之前先問。這三件事推導不出來，而猜錯的話整份要重寫：

1. **讀者是誰，他在什麼處境下會來讀？**
   最重要的一題。「給工程師看」太寬——是剛加入的人、正在整合 API 的人、還是凌晨三點在處理事故的人？處境決定寫法，而不是文件類型決定寫法。
2. **用什麼語言寫？**
   `docs/` 或 README 已經存在時跟著它走，不用問。完全沒有既有文件時要問——**README 的語言是團隊決定的，推導不出來**。
3. **是新寫，還是修既有的？**
   步驟三會盤點，但使用者常常心裡已經有目標檔案。先問一句可以省掉整輪搜尋。

**使用者說「幫這個專案補完整的文件」時，多問一句：現在最痛的是什麼？** 從最常被問的問題開始寫，比從 README 開始把每種類型補一遍有用得多——後者產出的是一套沒人讀的文件。

## 流程

### 步驟一：確認讀者，以及他來這裡想做什麼

不是「這是給工程師看的」——太寬了。要具體到情境，因為情境決定寫法：

| 文件 | 讀者的處境 | 這決定了什麼 |
| --- | --- | --- |
| README | 剛到，想知道這是什麼、能不能快速跑起來 | 五分鐘內要有第一個成功；背景知識不能預設 |
| API 文件 | 正在寫呼叫端，手上有 IDE | 要能複製貼上；錯誤情況比正常情況重要 |
| Runbook | **凌晨三點，正在恐慌** | 不能有任何需要思考的地方，每一步都是可執行指令 |
| 架構說明 | 要改動這個系統，想知道會踩到什麼 | 邊界與資料流優先於元件清單 |
| 上手指南 | 新人，什麼都不知道也不知道該問誰 | 要標出「去問誰」 |
| 註解 | 正在讀這行程式碼的人 | 只寫這行本身看不出來的事 |
| `CLAUDE.md` | AI agent，**會把內容當指令執行** | 見 `references/agent-docs.md` |

Runbook 那格最容易寫壞：白天寫的人覺得「這步很明顯」，凌晨三點的人不覺得。**寫 runbook 時假設讀者累、緊張、而且沒有 context。**

### 步驟二：判斷值不值得寫，以及寫哪一種

問一句：**把這份文件刪掉，讀者能不能從程式碼、型別、測試裡自己找到答案？**

能，就不要寫——那份文件的唯一命運是過期並開始說謊。判準與該寫／不該寫的對照見 `rules/what-earns-a-doc.md`。

註解的判斷比較細，另見 `rules/inline-comments.md`。

### 步驟三：盤點既有文件

```bash
ls README* CONTRIBUTING* docs/ 2>/dev/null
```

有既有文件時：**先讀，跟著它的語言、格式與深度走**，並優先改既有的而不是新增一份。同一件事有兩份說明，遲早會有一份是錯的，而讀者沒辦法知道是哪一份。

需要引用其他文件的內容時**放連結，不要複製**。複製過來的那份不會跟著更新。

### 步驟四：選一個不會悄悄過期的形式

這是最重要的一步，也是多數文件失敗的地方。對每一段內容問：**什麼會讓它變錯？變錯的時候有人會發現嗎？**

| 情況 | 該用什麼形式 |
| --- | --- |
| 會變錯，而且沒人會發現（參數列表、回傳結構、設定選項） | **不要寫散文。** 改成型別、schema、或從程式碼生成 |
| 會變錯，但會被發現（程式碼範例、指令） | 可以寫，但讓它**被執行**——doctest、範例專案納入 CI、指令寫進 Makefile |
| 不會變錯（為什麼這樣設計、限制條件、取捨、已知陷阱） | **散文最適合，而且只有散文寫得出來** |

第三列是文件最有價值的部分，因為它同時是最不會腐爛、也最不可能從程式碼推導出來的。**寫文件時把力氣放在第三列。**

### 步驟五：寫

各類型的骨架見 `templates/doc-types.md`，裡面也有 API 文件三種形式的選擇。

三個貫穿所有類型的寫法：

- **重要的先講。** 讀者多數不會讀完。第一段就要讓他知道這是什麼、要不要繼續讀
- **給可執行的東西，不要給描述。** 「設定認證」不如一段可以貼上去就跑的指令
- **寫出失敗的樣子。** 錯誤訊息、常見卡點、怎麼確認自己做對了——這些通常比正常流程更常被查閱

### 步驟六：自檢

- **刪除測試**：每一段刪掉之後，讀者能從程式碼 recover 嗎？能的話刪掉它
- **腐爛測試**：這段什麼情況會變錯？變錯時誰會發現？沒人會發現就換形式（回步驟四）
- **五分鐘測試**（README 專用）：照著做，五分鐘內有沒有第一個成功
- **凌晨三點測試**（runbook 專用）：每一步都是可執行的嗎？有沒有哪步需要判斷？

## 規則

- IMPORTANT：**只寫程式碼說不出來的東西。** why、限制、取捨、陷阱、去問誰——這些是文件的本體。what 交給程式碼、型別與測試。
- IMPORTANT：**會悄悄過期的內容不要寫成散文。** 參數列表、欄位結構、設定選項要嘛從程式碼生成，要嘛就是型別本身。手寫的那份一定會先過期。
- IMPORTANT：**跟著專案既有文件的語言與格式走**（沒有既有文件時見前置確認）。本 SKILL 的對話用繁體中文。
- IMPORTANT：**引用其他文件放連結，不要複製內容。** 複製的那份不會跟著更新，而讀者無法分辨哪份是對的。
- IMPORTANT：**Runbook 的每一步都要是可執行的。** 讀者的處境是凌晨三點、有人在等，任何需要思考的步驟都是一個會出錯的地方。
- NEVER：**不可寫複述程式碼的內容。** `// 把 count 加一` 這種註解、逐欄位重述型別的「API 文件」，寫的當下就沒有價值，之後還會變成謊言。
- NEVER：**不可為了「文件完整度」而寫。** 一份沒人讀的文件仍然要維護，成本是實的、收益是零。
- NEVER：**不可憑推測寫 why。** 寫不出某個設計的理由時去問，或直接省略那一段。編出來的理由會被後人當成決策依據。
- NEVER：**不可留下沒驗證過的指令或範例。** 貼上去跑不動的 quick start 比沒有 quick start 傷害更大——它會讓讀者以為是自己的環境有問題。

### 邊界情況

- **既有文件已經過期** → 先判斷它該改還是該刪。沒人維護得起的文件，刪掉比留著誤導好；刪的時候在原位留一行說明去哪找正確資訊
- **同一件事有兩份文件** → 選一份留下，另一份改成連結。不要兩邊都更新，那個習慣撐不過三個月
- **程式碼本身就很難懂** → 先問該不該重構（`code-refactor`）。用註解解釋一段可以改乾淨的程式碼，是把設計問題轉成維護負擔
- **要寫給 AI agent 讀的文件** → 見 `references/agent-docs.md`。它的讀者會把內容當指令執行，寫法與人類文件不同

# 各類型的骨架

每種文件的讀者處境不同（見 SKILL.md 步驟一的表），骨架跟著處境走，不是跟著慣例走。

## README

讀者剛到，想知道這是什麼、值不值得繼續看、能不能快速跑起來。

```markdown
# 專案名

<一到兩句：這是什麼、解決誰的什麼問題。不要寫「這是一個…的專案」，直接講功能>

## Quick Start

<能複製貼上就跑的最短路徑，目標五分鐘內看到第一個成功結果>

```bash
<實際驗證過的指令>
```

<跑完之後應該看到什麼——讓讀者能確認自己做對了>

## Usage

<最常見的兩三個使用情境，各配一段可執行的範例>

## Configuration

<只列常用的；完整清單連結到型別或 schema，不要在這裡手抄一份>

## Contributing

<怎麼跑測試、怎麼提交、有什麼慣例>
```

**Quick Start 是 README 唯一不能妥協的部分。** 讀者在這裡失敗就不會有第二次機會，而且他會以為是自己的環境有問題。指令一定要實際跑過。

「跑完應該看到什麼」常被省略，但它讓讀者能自我驗證——沒有這句，跑出奇怪結果的人不知道該不該繼續。

## API 文件

讀者正在寫呼叫端，手上有 IDE，需要能貼上去用的東西。

**先選形式，再寫內容**——這是 API 文件最重要的決定：

| 形式 | 什麼時候用 | 為什麼 |
| --- | --- | --- |
| **型別 + docstring** | 函式庫、內部套件、有型別系統的語言 | 跟程式碼在同一個檔案，改動時一起改；IDE 直接顯示；不會有第二份會過期的副本 |
| **OpenAPI / schema** | HTTP API，尤其有外部使用者時 | 可以生成 client、可以驗證請求、可以測；手寫的 endpoint 表做不到這些 |
| **手寫散文** | 只用來寫「什麼時候用哪個 endpoint」這種型別表達不了的事 | 其餘一律不要手寫——會過期而且沒人發現 |

不管哪種形式，這四件事都要寫，因為型別表達不了：

- **什麼時候該用這個**（跟相鄰的 API 差在哪）
- **錯誤情況**：什麼條件會失敗、回哪一種錯誤、該怎麼處理
- **副作用與限制**：rate limit、冪等性、是否會寫入、有沒有分頁
- **一個完整可跑的範例**（含認證那一段——那是最常卡住的地方）

**錯誤情況比正常情況更常被查閱。** 正常路徑讀者自己試就會了，卡住的時候才會回來翻文件。

## Runbook

讀者可能是凌晨三點，正在恐慌，有人在等他。

```markdown
# <事件或任務名稱>

## 什麼時候用這份

<具體的觸發條件，例如「alert `api_5xx_rate` 觸發時」。寫得夠具體，讓人能一眼確認自己來對地方>

## 開始前確認

- [ ] <需要的權限／VPN／存取>
- [ ] <需要通知誰>

## 步驟

1. <可執行的指令>
   預期看到：<輸出的樣子>
   沒看到的話：<跳到哪一步或找誰>

2. ...

## 回復（rollback）

<怎麼退回去，同樣是可執行的>

## 還是不行的話

<找誰、怎麼找、什麼時候該升級>
```

**每一步都要是可執行的，不能有需要判斷的地方。** 「檢查服務是否正常」是壞步驟；「跑 `curl -sf https://…/health`，應該回 `{"status":"ok"}`」是好步驟。

「預期看到」跟「沒看到的話」是 runbook 跟一般教學的差別——半夜的人需要的是決策樹，不是說明。

## 架構說明

讀者要改動這個系統，想知道會踩到什麼。

```markdown
# <系統／模組名>

## 這個系統做什麼

<一段，含它不做什麼——邊界比功能更難從程式碼看出來>

## 組成

<主要元件與各自的責任。用圖或條列都可以，但重點是責任劃分不是檔案清單>

## 資料流

<一個具體請求從進來到出去經過哪些地方。比靜態元件圖有用得多>

## 邊界與整合點

<跟外部系統的介面、契約、失敗時會怎樣>

## 已知的限制與陷阱

<擴展上限、隱含假設、踩過的坑>
```

最後一節是這份文件最有價值的部分，也是最容易被省略的。**元件清單讀原始碼看得出來，限制與陷阱看不出來。**

想寫「為什麼選這個架構」時停一下——那屬於 ADR，改用 `architecture-decision-records`，這裡放連結就好。

## 上手指南

讀者是新人，不知道自己不知道什麼，也不知道該問誰。

```markdown
# 上手

## 第一天：跑起來

<環境設定到能跑測試為止，每步都可執行>

## 系統長什麼樣

<三到五句加一張圖。不要在這裡展開架構，連結過去>

## 常見任務

<兩三個真實任務的完整走過一次：加一個 API endpoint、修一個 bug、發一次版>

## 誰負責什麼

<領域 → 人。這是新人最需要又最找不到的資訊>
```

「常見任務」用真實例子走一遍，比抽象說明有效得多——它同時教了流程、慣例與工具。

「誰負責什麼」會過期，所以放連結到會被維護的地方（團隊頁、CODEOWNERS）比手抄名單好。

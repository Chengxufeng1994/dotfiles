# 什麼值得寫成文件

## 唯一的判準

**把這段刪掉，讀者能不能從程式碼、型別、測試裡自己找到答案？**

能 → 不要寫。那段文字的唯一命運是過期，然後開始說謊。
不能 → 寫，而且這正是文件存在的理由。

下面所有內容都是這條判準的展開。

## 四類內容，只有兩類值得寫

| 內容 | 從程式碼推得出來嗎 | 判斷 |
| --- | --- | --- |
| **Why** — 為什麼這樣設計、否決了什麼 | 推不出來 | ✅ 文件的本體 |
| **限制與陷阱** — 什麼情況會壞、哪裡有隱含假設 | 推不出來（常常連寫的人都是踩過才知道） | ✅ 價值最高 |
| **What** — 有哪些參數、回傳什麼、有哪些欄位 | 推得出來 | ❌ 交給型別與生成 |
| **How** — 內部怎麼運作、逐行在做什麼 | 推得出來 | ❌ 交給程式碼本身 |

**第二類最容易被漏掉，但它救的時間最多。** 「這個 API 的 rate limit 是每分鐘 60 次，超過會回 200 但內容是空的」——這種事讀原始碼要讀很久，踩到要 debug 一整天，寫下來只要一行。

## 該寫的訊號

- **同一個問題被問了三次以上。** 這是最可靠的訊號——它證明了讀者存在、需求真實、而且口頭回答的成本已經在累積
- **有人（包含你自己）踩過同一個坑兩次**
- **決定背後有非顯而易見的限制**（「不能用 X，因為我們的 Y 版本不支援」）
- **新人上手時卡在同一個地方**
- **公開介面**——別人要靠它整合，而他們讀不到你的內部程式碼

## 不該寫的訊號

- **只是想「補齊文件」。** 沒有讀者的文件仍然要維護，成本是實的、收益是零
- **內容能從程式碼生成。** 手寫的那份會先過期，然後兩份互相矛盾
- **這段程式碼快被改掉了**
- **寫下來是為了證明工作有做。** 這種文件通常沒有具體讀者，所以也沒有具體內容
- **要解釋的是一段可以重構乾淨的程式碼。** 那是把設計問題轉成維護負擔，先看 `code-refactor`

## 腐爛測試

決定內容之後、動筆之前，對每一段問兩件事：

1. **什麼會讓這段變錯？**
2. **變錯的時候有人會發現嗎？**

第二題的答案決定形式：

| 會變錯 | 有人發現 | 該怎麼做 |
| --- | --- | --- |
| 會 | 不會 | **最危險。** 不要寫散文——改成型別、schema、或從程式碼生成 |
| 會 | 會（測試紅、build 壞） | 可以寫，但要讓它真的被執行：doctest、範例納入 CI、指令寫進 Makefile |
| 不會 | — | 散文最適合，而且只有散文寫得出來 |

第一列是文件債的主要來源。典型例子：手寫的參數表、設定選項清單、目錄結構圖、環境變數列表。它們都是「今天正確、三個月後錯了、而且沒有任何機制會告訴你」。

**遇到第一列有三條路**，按優先序：

1. **刪掉**，讓讀者去看型別或 `--help`
2. **生成**，從 schema／型別／CLI 定義產出
3. **標記**，寫明「以 `config.ts` 為準，此處僅供概覽」——把它降級成索引而不是事實來源

## 一份文件的壽命

寫之前想一下這份文件會活多久，它會改變你的寫法：

- **會活很久**（架構的 why、領域概念、決策脈絡）→ 值得花時間寫好，而且不要放會過期的細節進去污染它
- **會活到下次改版**（quick start、設定說明）→ 寫精簡，並綁在會被執行的東西上
- **只活到這次上線**（遷移步驟、暫時的 workaround）→ 寫在 PR 或 issue 裡，不要進 `docs/`。放進去就沒有人會刪，然後它會永遠誤導人

最後一項最常被違反。**臨時性的說明放進長期文件，是文件目錄腐爛最常見的起點。**

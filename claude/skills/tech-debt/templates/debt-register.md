# Debt Register

一份**會被更新的活文件**，不是一次性的稽核報告。建議放 `docs/tech-debt.md` 並進版本庫——放在票務系統裡的技術債會沉到 backlog 底部，放在版本庫裡的會在每次 review 相關檔案時被看見。

## 骨架

```markdown
# Tech Debt Register

最後更新：YYYY-MM-DD

## 現在就處理（40+）

### [簡短標題]
- **類別**：Architecture
- **分數**：Impact 5 + Risk 4 = 9 × (6−2) = 36
- **成本**：[具體的、可驗證的損失]
- **當初為什麼借**：[知情妥協的理由；沒有理由的話它是 mess，不該在這裡]
- **歸宿**：排程 → [具體時間或迭代] · 負責人：[誰]

## 綁觸發條件（15–24）

### [簡短標題]
- **類別**：Test
- **分數**：…
- **成本**：…
- **歸宿**：觸發 → 下次動到 `internal/billing/` 時一併處理

## 已接受（明確決定不處理）

### [簡短標題]
- **成本**：…
- **為什麼接受**：[理由]
- **什麼情況會改變主意**：[具體條件]
```

三個區塊對應三種歸宿。**沒有第四個區塊**——沒有「待評估」「有空再說」。一項東西進不了這三格，就代表資訊不足，先去補資訊而不是先登記。

## 單項怎麼寫

### 「成本」要可驗證

| 差 | 好 |
| --- | --- |
| 這個模組很難維護 | 結帳邏輯散在 3 個檔案，每次改價格規則都要同步修改；上季漏改造成 2 次線上問題 |
| 測試覆蓋率太低 | `payment/` 沒有整合測試，過去半年 4 個 bug 是使用者回報而非測試抓到的 |
| 依賴太舊 | `axios@0.21` 有已知 CVE，且與我們要升的 Node 22 不相容 |

判準：**這句話能不能讓一個不熟這段程式碼的人同意它是問題？** 右欄可以，左欄需要對方先相信你。

### 「當初為什麼借」是債與 mess 的分界

寫得出來 → 是債，留在 register。
寫不出來 → 是 mess，從清單刪掉，在日常重構裡處理。

這一欄還有一個作用：**它常常會揭露那個理由已經不成立了**。「當初趕上線所以沒抽出來，打算下個月處理」——如果那是兩年前寫的，這一項的優先序應該重估。

### 「歸宿」不能是願望

| 差 | 好 |
| --- | --- |
| 之後處理 | 排程 → 2026-Q3 · 負責人：@benny |
| 有機會就重構 | 觸發 → 下次動到 `internal/billing/` 時一併處理 |
| 應該要修 | 接受 → 影響僅限開發體驗，等到團隊超過 5 人再議 |

## 維護

**每次動到相關程式碼時順手更新**，不要等定期盤點。定期盤點會變成一次做完然後半年不管。

三種該更新的時機：

- 還完了 → 刪掉那一項（不要留「已完成」區塊，那只會讓文件變長）
- 借了新的債 → 當下就登記，這時「為什麼借」最清楚
- 某項連續三次被跳過 → **這是訊號不是失誤**。要嘛它的分數評高了，要嘛它其實該被標成「接受」

最後一項是這份文件保持可信的關鍵。**一項債如果一直被跳過卻一直留在「現在就處理」，整份 register 就開始說謊**，然後沒有人再認真看它。

## 給非技術讀者的版本

需要向主管論證時，不要給 register 本身。抽出三到五項，改寫成：

```markdown
## 建議處理的三項

1. **結帳邏輯分散** — 每次改價格規則約多花 2 人天，且上季造成 2 次線上問題。
   整理需 1 週，之後同類改動可省約 60% 時間。

2. ...

## 不建議現在處理

- [某項] — 目前只影響開發體驗，沒有線上風險。等團隊擴編再議。
```

只講**時間、金錢、風險**。不要出現 SOLID、耦合、抽象層這些詞——它們對這個讀者是雜訊，而且會讓對話偏離到技術辯論。

「不建議現在處理」那一節不要省略：**它證明你在做取捨而不是討預算**，這比多爭取到一項要重要。

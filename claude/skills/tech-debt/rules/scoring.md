# 評分

## 公式

```
優先序 = (Impact + Risk) × (6 − Effort)
```

三個維度各 1–5 分。Effort 反轉的用意是：**同樣的痛，能便宜解決的先做**——早期的勝利會買到繼續處理債務的信任。

分數的功能不是精確排序，是**逼你把感覺拆成三個獨立的判斷**。兩項都覺得「很重要」的時候，拆開來看常會發現一個是 Risk 高、另一個是 Impact 高，而它們適合的處理時機不同。

## Impact — 它每天拖慢多少事

問：**這件事現在每週吃掉多少時間？**

| 分 | 判準 |
| --- | --- |
| 5 | 每次碰到相關功能都被拖慢；跨多人多團隊 |
| 4 | 常態性拖慢某個模組的開發 |
| 3 | 每隔幾週會撞到一次 |
| 2 | 偶爾造成困擾 |
| 1 | 幾乎不影響日常工作 |

**估不出時間就給低分。** 說不出成本的東西通常成本不高——真正在痛的事，痛的人講得出具體例子。

Impact 是唯一可以用觀測驗證的維度：看 `git log` 的改動熱點、看 PR 的 review 來回次數、看同類 bug 的重複出現。

## Risk — 不處理的話會發生什麼

問：**如果一直不處理，最壞會怎樣？**

| 分 | 判準 |
| --- | --- |
| 5 | 資料遺失、資安漏洞、或會造成 SEV1 的單點故障 |
| 4 | 會造成使用者可見的故障，而且復原很慢 |
| 3 | 會造成偶發問題，但影響可控 |
| 2 | 只影響開發體驗，不影響線上 |
| 1 | 純美觀 |

**Impact 與 Risk 不是同一件事。** 一個沒有測試的付款流程可能 Impact 低（很少改）但 Risk 極高（改了就可能出事）。一份難讀的工具程式可能 Impact 高（天天碰）但 Risk 低（壞了立刻知道）。分開評才看得出這個差異。

## Effort — 修起來多難

| 分 | 判準 |
| --- | --- |
| 1 | 幾小時，單一檔案 |
| 2 | 一兩天，範圍清楚 |
| 3 | 一週內，跨幾個模組 |
| 4 | 數週，需要協調 |
| 5 | 數月，或需要遷移資料 |

**估不準時往高估。** 重構的實際成本幾乎總是超過直覺，因為呼叫端與測試的連鎖影響在估的時候看不見。

Effort 4 以上的項目要考慮**能不能切小**——切成三個 Effort 2 的階段性成果，比一個 Effort 5 的大工程更可能真的被做完。

## 分數怎麼用

| 分數 | 大致意義 |
| --- | --- |
| 40+ | 現在就排 |
| 25–39 | 排進下一兩個迭代 |
| 15–24 | 綁觸發條件（「下次動到就處理」） |
| < 15 | 多數應該標成「接受」，不要留在待辦裡 |

**這是參考不是規則。** 分數會被高 Risk 低 Effort 的項目沖高，但有些 Risk 5 的東西（資安）不管分數多少都該先做。

**不要為了讓某項排前面而調分數。** 想調的時候，通常代表你有一個沒寫進三個維度的理由——把那個理由寫下來，它比分數有價值。

## 三個評分時的陷阱

**把「我不喜歡」評成 Impact 高。** 審美偏好不是成本。判準是能不能講出一個具體的、別人也會同意的損失。

**把 Risk 評成「理論上可能出事」。** 所有程式碼理論上都可能出事。Risk 問的是**不處理的話，在可預見的使用方式下會發生什麼**。

**忘記 Effort 包含驗證成本。** 改動本身兩小時、但要補的測試與回歸驗證要兩天，Effort 是兩天不是兩小時。

## 什麼時候不必評分

只有三五項的時候直接排序就好，不必套公式。**評分是給「項目多到直覺排不出來」用的工具**，項目少的時候它只是儀式。

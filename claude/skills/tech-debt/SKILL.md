# Tech Debt

「債」這個字是精確的：**你知情地借了，有理由，而且有本金要還。**

多數「技術債清單」其實是 mess 清單——意外累積的髒亂，沒有人決定過要借它。這個區別不是文字遊戲，它決定了處理方式：**債要排程還，mess 要在經過時順手清掉。** 把兩者混在一起，清單會長到沒人看，然後兩種都不會被處理。

第二件事同樣重要：**一份沒人行動的債務清單，比沒有清單更糟。** 它把模糊的不安轉成一份白紙黑字、被忽略的義務——既提供了虛假的安心（「我們知道這件事」），又持續消耗士氣。所以本 SKILL 的每一項都必須有歸宿：排程、觸發條件、或明確接受。不允許「有空再說」。

## 使用時機

- 要盤點一個專案有哪些技術債
- 有一堆想改的東西，要決定先改哪個
- 在猶豫某個妥協該不該現在處理
- 要向非技術的人論證重構的必要性
- 剛做了一個知情的妥協，想記下來

## Skill Boundaries

- 決定要改之後**怎麼改** → 改用 `code-refactor`
- 某個架構決策的理由與否決的選項 → 改用 `architecture-decision-records`（ADR 記「為什麼這樣決定」，本 SKILL 記「我們知道這裡妥協了」）
- 只是想讓一段程式碼更好讀 → 改用 `code-simplification`
- 依賴套件過期、有漏洞 → 改用 `security-and-hardening`；但把它登記成債仍然適用
- 本 SKILL 管 **盤點、分類、排序、以及讓清單真的被還**

## 前置確認（Ask User）

使用者沒講清楚時，開始之前先問。這三件事決定產出的規模與形狀，而它們都在使用者腦裡，不在 repo 裡：

1. **範圍**：要盤點整個專案，還是判斷某一項該不該處理？
   兩者的成本差一個數量級。「這段要不要重構」只需要走步驟一與三；全面盤點要走完整流程。
2. **現在最痛的是什麼？**
   從這裡開始，不要從全面掃描開始。**全掃描產生的是一份沒人讀的清單**——它會把真正在痛的三項稀釋在四十項裡面。使用者答不出來時，改用步驟二的改動熱點當入口。
3. **產出給誰看？**
   團隊自用 → 用 `templates/debt-register.md` 的完整格式。要向非技術主管論證 → 只講時間、金錢、風險，格式見同一份模板的最後一節。

## 流程

### 步驟一：分清楚債與 mess

| | 債 | Mess |
| --- | --- | --- |
| 怎麼來的 | 知情的取捨（趕上線、當時資訊不足） | 意外累積、沒人決定過 |
| 有沒有理由 | 有，而且說得出來 | 沒有 |
| 怎麼處理 | 登記、排序、排程還 | 下次經過時順手清掉 |

**Mess 不要進清單。** 它進去只會稀釋掉真正需要決策的項目。變數命名亂、少了幾個註解、某個函式有點長——這些在 `code-refactor` 的日常流程裡處理就好。

例外：mess 累積到會拖慢工作時，它就有了本金，這時登記成債。判準是**你說得出它每週花掉多少時間**。

### 步驟二：盤點

債不會自己浮出來，用這四個來源挖：

| 來源 | 怎麼看 | 挖出什麼 |
| --- | --- | --- |
| **改動熱點** | `git log --format= --name-only \| sort \| uniq -c \| sort -rn \| head -20` | 常改又難改的檔案，是投報率最高的債 |
| **抱怨** | 團隊反覆提到的「每次動那裡都很痛」 | 有實際成本、而且有人在乎 |
| **繞路** | 程式碼裡的 workaround、`// 暫時`、被複製而非重用的邏輯 | 當初借的地方 |
| **事故** | postmortem 的行動項裡沒做完的 | 已經證明有風險 |

第一個來源最客觀。**很爛但沒人動的程式碼不是債**——它不產生利息。

### 步驟三：分類與評分

六類：**Code、Architecture、Test、Dependency、Documentation、Infrastructure**。分類的用途不是整齊，是看出**債集中在哪一類**——全部集中在 Test 跟 Infrastructure，代表問題不在程式碼而在工程實務。

評分與計算方式見 `rules/scoring.md`。

### 步驟四：給每一項一個歸宿

這是本 SKILL 最重要的一步。每一項只能是三種之一：

1. **排程** — 進到某個具體的迭代或時間區間
2. **觸發條件** — 「下次動到這個模組時一起處理」「當 X 超過 Y 時處理」
3. **明確接受** — 「我們決定活在這個問題裡，因為 Z」，並寫下什麼情況會讓我們改變主意

**沒有第四種。** 「有空再說」等於不會做，而它留在清單裡會讓整份清單失去可信度。

第三種被低估了。明寫「接受」比讓它躺在待辦裡假裝會被處理誠實得多，也讓後來的人知道這件事被評估過。

### 步驟五：產出 register

用 `templates/debt-register.md`。它是一份會被更新的活文件，不是一次性的稽核報告。

**清單長度要能被讀完。** 超過 15 項就代表分類不夠嚴、mess 混進來了，或該把低分項目直接標成接受。

## 規則

- IMPORTANT：**每一項都要有歸宿**——排程、觸發條件、或明確接受。沒有「有空再說」這個選項，因為它會讓整份清單失去可信度。
- IMPORTANT：**用具體成本論證，不用形容詞。** 「這個模組很爛」說服不了任何人；「每次改結帳都要同步改三個地方，上季因此漏改造成兩次線上問題」可以。
- IMPORTANT：**只登記有利息的債。** 很爛但沒人動的程式碼不產生成本，登記它只會稀釋清單。
- IMPORTANT：**分類是為了看出集中在哪。** 六類的分佈本身就是診斷——債全在 Test 與 Infrastructure，代表要修的是工程實務不是程式碼。
- NEVER：**不可把 mess 登記成債。** 意外累積的髒亂在日常重構裡順手處理，進清單只會把它撐到沒人看。
- NEVER：**不可寫沒有負責人或觸發條件的項目。** 那是願望不是計畫。
- NEVER：**不可用這份清單當成不重構的藉口。** 登記不等於處理——如果一項債連續三次被跳過，那代表它該被標成「接受」，或該重新評估分數。
- NEVER：**不可在同一次改動裡混入「順手還債」與功能開發。** 分開提交，理由與 `code-refactor` 相同：混在一起就無法歸因。

### 邊界情況

- **要向非技術主管論證** → 只用時間與風險說話：「這件事每個月吃掉約 X 人天」「不處理的話下次 Y 發生時我們沒有辦法快速恢復」。不要出現 SOLID、耦合、技術名詞
- **債太多不知從何下手** → 挑一個**分數高且範圍小**的先做完。完成一項的示範價值大於同時推進五項
- **這段程式碼即將被取代** → 不要登記。確認它的壽命再決定
- **剛做完一個知情的妥協** → 當下就登記，附上當時的理由與什麼條件下該還。事後補的債務紀錄會漏掉最重要的東西：**為什麼當時那樣做是對的**

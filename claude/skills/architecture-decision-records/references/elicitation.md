# 怎麼問出真正的取捨

## 為什麼這一步不能省

照著使用者說的話填模板，產出的是他已經知道的東西。ADR 的讀者不是他，是三個月後接手的人、或是明年想推翻這個決定的人——那個人需要的資訊，恰恰是使用者當下覺得「太明顯所以不用講」的部分。

所以這一步的姿態是**追問，不是抄寫**。你是在幫他把腦中的東西挖出來，不是幫他打字。

## 三個必須問到的東西

### 一、真正評估過哪些方案

先問開放的：「除了 X，當時還認真看過什麼？」

答案是「沒有，就直接選了」時，**不要當成失敗**。那本身就是有價值的紀錄——寫進 Context：「選 X 是因為團隊已經在用，沒有評估其他選項」。誠實的「沒比較」勝過編出來的比較表。

答案有列出選項時，追一句：「那個時候 Y 看起來最吸引人的地方是什麼？」這句話的作用是**分辨真評估與事後合理化**。真的評估過，他會講得出 Y 的好；只是隨口提到 Y，他會答不出來或只重複 Y 的缺點。

### 二、每個被否決方案的最強論點

這是**稻草人測試**，也是整份 skill 最重要的一問。

對每個要寫進 Alternatives 的方案問：**「如果要你替這個方案辯護，你會說什麼？」**

- 講得出來 → 這是真的候選方案，寫進去，而且把那個最強論點寫進 Pros
- 講不出來 → 它是稻草人，**刪掉**

刪掉之後 Alternatives 只剩一個選項也沒關係。「只認真評估過 PostgreSQL 和 MySQL」是誠實的紀錄；硬湊三個選項讓表格好看，會讓後人以為 MongoDB 被嚴肅評估並否決過——然後他們就不會再去評估它。**假的比較會關掉未來的選項。**

### 三、這個決定會讓什麼變難

問法要具體，不要問「有什麼缺點」（會得到罐頭答案）：

- 「半年後如果要換掉這個決定，最痛的會是哪一段？」
- 「這個選擇讓哪一類需求從此變麻煩？」
- 「新人上手時，這個決定會在哪裡絆到他們？」
- 「什麼情況下你會後悔這個決定？」

最後一句最有效，因為它直接問**推翻條件**——而推翻條件正是未來讀者最需要的東西。它常常會問出可以寫進 Risks 的內容：「如果寫入量成長十倍，這個方案會撐不住」。

## 追問的分寸

**問到夠用就停。** 三個問題各追一輪通常就足夠，超過會讓使用者覺得在被盤問。判準是：**Alternatives 有真實的 Pros、Consequences 有具體的負面**，就可以去寫草稿了。

**不要為了填滿模板而問。** 模板的章節是選用的（見 `templates/adr.md` 的觸發條件），問不出 Security 影響通常是因為這個決策真的沒有安全面向，不是因為問得不夠。

**使用者急著要成品時**，先用他給的資訊寫一版草稿，把不確定的地方用 `> 待確認：...` 標出來，讓他在草稿上補。這比先盤問五輪再開始寫更順——**有草案才問得出好問題**，空手發問只會得到空泛答案。

## 幾組實際對話

**分辨真評估**

> 「我們選了 Kong 當 API Gateway。」
>
> → 「那時候 AWS API Gateway 看起來最吸引人的地方是什麼？」
>
> 「呃……託管的吧，不用自己維運。」
>
> → 這是真的候選。寫進 Alternatives，Pros 放「fully managed, no infrastructure to operate」，Why not 要對應到這個 Pros 為什麼不夠——通常是「我們需要跑自訂 plugin，託管方案改不動」。

**問出負面代價**

> 「用 event sourcing，可稽核性和時序查詢都解決了。」
>
> → 「什麼情況下你會後悔這個決定？」
>
> 「大概是如果 event schema 要改的話……那會很痛，因為已經寫進去的改不了。」
>
> → 這句直接變成 Consequences 的 Negative 加 Risks，而且是使用者自己說的，不是你猜的。

**處理「沒有替代方案」**

> 「就用 PostgreSQL 啊，還能用什麼。」
>
> → 「所以是團隊本來就在用、沒有特別比較？還是有看過別的但很快排除了？」
>
> 「本來就在用。」
>
> → Context 寫「Team already operates PostgreSQL for three other services」，Alternatives 只留一句「No alternatives were seriously evaluated; existing operational familiarity dominated」。這比編一個 MongoDB 對照組誠實得多。

## 決策已經寫在程式碼裡的時候

補記舊決策時，使用者常常不記得細節了。這時**先自己讀程式碼建立假設，再拿假設去問**——「看起來是用了 X 而不是 Y，是因為 Z 嗎？」比「當初為什麼選 X？」好回答得多。

從程式碼可以推出 Decision 與部分 Context；推不出來的永遠是 Alternatives 與 Consequences，那兩段只能問。問不到就照實寫「backfilled; original alternatives not recorded」，不要用推測填空。

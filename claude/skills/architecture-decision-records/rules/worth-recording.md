# 值不值得記

## 唯一的判準

**半年後有人想改這個決定的時候，會需要知道理由嗎？**

會 → 記。不會 → 不記。

下面的分類與清單都是這條判準的具體化，用來快速判斷，不是獨立規則。

## 三個信號

一個決定值得記，通常同時滿足這三項：

1. **有真正的替代方案。** 只有一條路可走的事不叫決策，叫實作。
2. **改起來很貴。** 換掉要動很多地方、要遷移資料、要協調別的團隊。便宜到隨時能改的事不需要紀錄。
3. **理由從程式碼看不出來。** 這是最關鍵的一條——如果讀 code 就知道為什麼，ADR 只是重複。

第三項是最常被忽略的過濾器。「我們用 TypeScript」看 `tsconfig.json` 就知道；「我們在 50 個元件之後才導入 TypeScript，因為 PropTypes 只有執行期檢查，型別不符的 bug 已經佔了三成回報」才是 ADR。

## 分類參考

| 類別 | 例子 |
| --- | --- |
| **技術選型** | 框架、語言、資料庫、雲供應商、ORM |
| **架構模式** | 單體 vs 微服務、事件驅動、CQRS、分層方式 |
| **API 設計** | REST vs GraphQL、版本策略、認證機制、分頁方式 |
| **資料建模** | schema 設計、正規化取捨、快取策略、分片鍵 |
| **基礎設施** | 部署模型、CI/CD、監控堆疊、環境切分 |
| **安全** | 認證授權策略、加密方式、機密管理 |
| **測試** | 測試框架、涵蓋率目標、E2E 與整合的比重 |
| **流程** | 分支策略、review 流程、發版節奏 |

最後一列常被漏掉——流程決策同樣有替代方案、同樣難改、理由同樣看不出來。「我們用 trunk-based 而不是 GitFlow」值得一份 ADR。

## 不要記的

| 不記 | 為什麼 |
| --- | --- |
| 變數命名、程式碼格式 | linter 的職責，而且沒有替代方案要權衡 |
| 次版本升級、例行依賴更新 | 沒有決策，只有維護 |
| 單一函式的實作方式 | 改起來便宜，讀 code 就知道 |
| 設定值調整 | 除非那個值背後有非顯而易見的權衡（那就記那個權衡） |
| 修 bug | 除非修法本身是個架構取捨 |

**過度記錄跟不記錄一樣糟。** 一個塞了四十份的 `docs/adr/`，裡面三十五份是瑣事，會讓真正重要的五份沉下去——然後沒有人再讀這個目錄，等於全部都沒記。

## 灰色地帶怎麼判

**「這是不是太小了？」** → 用第三個信號：理由從程式碼看得出來嗎？看得出來就不記。

**「已經是業界慣例了還要記嗎？」** → 記，如果你們**偏離**了慣例；不記，如果你們跟著慣例走。ADR 的價值在解釋為什麼不走預設路徑。

**「這個決定可能兩個月後就改了。」** → 更該記。短命的決策最需要留下當時的限制條件，否則兩個月後沒有人記得為什麼要改回來，也不知道當初的問題解決了沒。

**「決策是別人做的，我只是實作。」** → 值得記就記，Deciders 欄位寫實際做決定的人。ADR 記錄的是決策，不是誰打字。

**一組相關的小決定** → 合成一份。「API 設計慣例：REST、複數名詞資源、cursor 分頁、header 版本」是一份 ADR，不是四份。判準是它們會不會一起被推翻——會的話就是一個決策。

# ADR 自檢

草稿交給使用者之前跑一遍。也用來 review 別人寫的 ADR。

存在的理由是：**寫壞的 ADR 通常不是缺了某一節，而是每一節都在但沒有一節說出程式碼說不出的事**。格式完整、四節俱全、讀起來像模像樣，卻是一份把既成事實重述一遍的文件。這種空轉從表面看不出來，只能用測試逼出來。

## 六項測試

| 檢查項 | 判斷動作 | 沒過的症狀 |
| --- | --- | --- |
| Alternatives 不是稻草人 | **辯護測試**：對每個被否決的方案，講得出支持它的最強論點嗎？ | Pros 寫得敷衍，或 Pros 其實是缺點的委婉版 |
| Consequences 有負面 | **代價測試**：這個決定讓什麼變難了？ | Negative 是空的，或寫「需要學習成本」這種通用句 |
| Context 不含決策 | **順序測試**：Context 裡的每一句，在決定做出**之前**就成立嗎？ | Context 已經在論證結論，變成 Decision 的前言 |
| 理由不在程式碼裡 | **重複測試**：讀 code 或設定檔能不能得到同樣的資訊？ | 整份 ADR 等於 `package.json` 的散文版 |
| Why not 對得上 Context | **對應測試**：每個「Why not」能不能指回 Context 裡的某個限制條件？ | 否決理由憑空出現，或用了 Context 沒提過的標準 |
| 兩分鐘讀得完 | **計時測試**：Context 超過十行嗎？整份超過一頁半嗎？ | 寫成技術報告，附了 benchmark 全文 |

第三項最常被違反且最難自己發現。Context 該寫的是**決策前的世界**——問題、限制、當時的事實。一旦出現「因此我們需要一個能……的方案」，就已經滑進 Decision 了。這會讓 Alternatives 看起來全都不合格，因為 Context 已經照著答案寫好了條件。

## 各節的反模式

### Context

| 反模式 | 為什麼壞 |
| --- | --- |
| 「我們需要一個現代化的資料庫」 | 「現代化」不是限制條件，無法用來否決任何方案 |
| 直接從結論寫起 | 讀者無法判斷這個決定合不合理，只能接受 |
| 附上完整 benchmark 數據 | 放 `References` 連結，Context 只留結論數字 |
| 沒有時間感 | ADR 是有時效的判斷。「當時 MongoDB 還不支援多文件交易」這種限定要寫出來 |

### Decision

| 反模式 | 為什麼壞 |
| --- | --- |
| 「使用 ORM」 | 不具體。是哪個？ |
| 「我們將會採用 X」 | 未來式。ADR 記錄生效中的狀態 |
| 一段話講三個決定 | 一份 ADR 一個決策，否則沒辦法單獨 supersede |

### Alternatives

| 反模式 | 為什麼壞 |
| --- | --- |
| 每個方案的 Pros 都很弱 | 稻草人。真評估過的方案一定有真實吸引力 |
| 「Why not: 不適合我們的需求」 | 哪個需求？對不上 Context 就等於沒說 |
| 為了湊三個而列的選項 | 假比較會讓後人以為它被否決過，從此不再考慮 |
| 完全省略這一節 | 沒有替代方案的「決策」是實作。回頭確認這值不值得記 |

### Consequences

| 反模式 | 為什麼壞 |
| --- | --- |
| 只有 Positive | 只有好處的決策不存在。取捨還沒想清楚 |
| 「Negative: 有學習曲線」 | 通用到能貼在任何 ADR 上，零資訊量 |
| 把 Negative 都寫成已解決 | 「缺點是 X，但我們用 Y 解決了」——那就不是 Negative，是 Implementation Note |
| 沒有推翻條件 | 「什麼情況下這個決定會失效」是後人最需要的一句 |

## 誠實原則

六項全過而且找不到任何可補的地方時，先懷疑自己在敷衍——尤其是辯護測試，它在實務上的通過率遠低於直覺。

某一項確實沒過但使用者接受（例如他就是不想寫替代方案），照他的意思產出，但要明講你跳過了哪一項。安靜地放過會讓那份 ADR 帶著一個看不見的洞進入版本庫，而 ADR 的讀者沒有辦法知道哪裡不可信。

# 撰寫 plan

把一份已收斂的 spec，轉成**可逐條執行、每條都能驗證**的實作任務清單，寫入 `docs/<domain>/<feature>/plan.md`。

核心理念：plan 的價值不在「想得多周全」，而在「每一步都知道做完沒」。一份沒有驗證方式的任務清單，跟沒有 plan 差不多——執行時還是得憑感覺判斷進度。

## 範圍：這是任務拆解，不是設計文件，也不是實作

這份文件回答**要做哪些事、什麼順序、每件事怎麼驗證完成**。

它**不**是：

- **不是 spec**：不重述問題背景、目標、使用者價值。那些在 spec.md，引用即可。
- **不是完整設計文件**：架構圖、資料模型、API 契約不在這裡展開。若某個任務需要一個非顯而易見的技術決策，就在該任務下用一兩句寫清楚選了什麼、為什麼；不要長成獨立的架構章節。
- **不是 patch**：不要把實作程式碼貼進 plan。plan 是路線圖，寫成「在 `x.go` 新增 `ParseRule`，處理空字串與重複鍵」就夠了；貼上整份實作只會讓 plan 在第一次改動後就過期。

為什麼守住這條線：plan 的讀者是「即將動工的人」（可能是你自己、隊友，或下一個 session 的模型），他要的是可以照著跑、跑完能勾掉的清單。混進背景敘述會稀釋訊號，混進實作程式碼會讓文件比程式碼更早腐爛。

## 語言

plan 內容與章節標題，跟著使用者當下溝通的語言走（預設繁體中文；若使用者以英文溝通，整份 plan 改用英文）。技術名詞、檔名、指令維持原文，不要翻譯。

## 執行流程

### 第一步：讀 spec

找到來源 spec（通常是 `docs/<domain>/<feature>/spec.md`）並完整讀過。它對「要做什麼」是權威，**不要在 plan 裡改寫或推翻它**——若讀到覺得有問題的地方，提出來讓使用者決定，不要自己修正。

從 spec 抓出這幾樣，它們是後面拆任務的骨架：

- **功能需求**（FR-N 及優先級）——決定要拆出哪些任務、哪些這次不做
- **驗收標準**——直接餵給任務的 verify
- **非功能需求／限制**——常常是獨立任務（效能量測、i18n、相容性）
- **開放問題／[待確認]**——這些是計畫上的地雷，要在 plan 明確標出來，不要假裝已解決

**找不到 spec 時**：先問使用者要「先跑 `writing-a-spec` 補一份」還是「直接依現有需求描述拆任務」。若選後者，照做，並在 plan 的前置確認註明「無 spec 來源，需求依據為 <出處>」——讓後續讀者知道這份 plan 的地基有多穩。

### 第二步：探查專案（決定 plan 能不能真的被執行）

**不要跳過這步。** 沒有探查就寫出來的 plan，檔案路徑、分層命名、驗證指令全是猜的——執行時每一條都要重新查，plan 等於沒用。

要查清楚三件事：

1. **相似的既有實作**——找 2～3 個功能形狀相近的既有模組（同類 endpoint、同類 job、同類 UI 元件），看它怎麼分層、檔案放哪、怎麼命名。新任務照著它走，而不是照你偏好的架構走。這也順便回答了「這個專案到底是不是 DDD／Clean Architecture」——照 repo 的實際樣子，不要預設。
2. **驗證指令**——測試、lint、build、type check 各怎麼跑（Makefile／package.json scripts／justfile／CI 設定）。verify 欄位只能寫**這個 repo 真的跑得動的指令**。
3. **已經存在的東西**——spec 要的能力是否已有一半做好了？有沒有可直接複用的工具函式、既有 migration 機制、既有錯誤型別？重複造輪子的任務要在這步就刪掉。順帶留意半成品：一個只丟 `NotImplementedError` 或回傳空值的函式，可以當形狀參考，但不能當成可依賴的基礎。

探查完要守住一條底線：**plan 裡出現的每一個既有檔案、目錄、指令、註冊點，都必須是你真的看到的。** 需要它但找不到，就標 `[待確認]` 並寫明它擋住哪個任務。這裡最常見的失手不是說謊，而是在沒想到要查的地方憑架構直覺補一句「對齊既有慣例」——讀者會當成事實去找，然後找不到。寧可寫「repo 內未見 X，需確認」，也不要讓一句含糊的話混過去。

把探查結果濃縮成幾行寫進 plan 的「前置確認」，讓讀者知道這份計畫依據什麼假設排出來的。

### 第三步：澄清（最多 3 題，且只問 repo 答不出來的）

多數技術問題應該由第二步的探查回答，不是問使用者。只有**真正需要人做決定**的才問——例如兩個都合理的做法、要不要向後相容、這次要做到 P1 還是只做 P0。

一次一題，格式：

---
**[Q N/3]** [針對一個決策點的具體問題]

**推薦：X** — [1–2 句推薦理由，理由要來自你在第二步看到的實際狀況]

| 選項 | 說明 |
|------|------|
| A | … |
| B | … |
| C | 其他（請描述） |

回覆代號即可，或說「yes」接受推薦。

---

**降級路徑**：若使用者說「直接寫／不用問」，或當下無法互動，就以合理假設直接產出，把假設寫進「風險與未定」並標 `[待確認]`。

### 第四步：拆任務

讀 `templates/plan-template.md` 作為骨架。拆解原則：

- **一個任務 = 一個可獨立驗證的成果**，大約是一次能 commit 的量。「實作匯出功能」太大；「新增 `ExportJob` 型別與其驗證規則」剛好。
- **每個任務都要有可執行的 verify**。優先用指令（`make test-billing`、`pnpm test src/export`），指令驗不到的才用可觀察結果（「呼叫 `POST /v1/exports` 回 202 且 DB 出現 pending 紀錄」）。寫不出 verify，通常代表這個任務切得不對，回頭重切。
- **需要有人動手的前提，本身就是任務**。「先跑 `go mod tidy`」「補上缺的設定檔」「把某個空實作補完」這類事若不做就會擋住第一個任務，就升格成 T0 並給它 verify。寫進「前置確認」會被當成背景資訊讀過去、沒人執行，然後第一個任務就因為不相干的原因失敗。「前置確認」只放**不需要動作**的事實：既有分層長怎樣、驗證指令是什麼、哪些東西可複用。
- **順序由相依決定，不是由層級決定**。先做被依賴的、先做能讓後面任務有東西可測的。若專案跑 TDD，第一個任務通常是「寫出會紅的測試」。
- **標出可平行的任務**，讓多人或多 agent 分工時不用重推一次相依關係。
- **每個 P0 需求都要有任務對應**。P1／P2 若這次不做，在驗收對照表明確標「本次不做」，而不是默默省略——漏掉和刻意不做，對讀者是完全不同的訊息。
- **只指涉真的存在的東西**。任務裡寫到的既有檔案、模組、註冊點，必須來自第二步的探查；推測出來的一律標 `[待確認]`。
- **範圍擴張要講明**。新增依賴套件、新建目錄、引入新工具（測試框架、migration 工具、CI job）都不是順手做掉的事——它們影響的是整個專案而不只這個功能，要獨立成任務並註明是「新增」而非「沿用」，讓 reviewer 有機會擋。
- **任務的產出是程式行為的改變**，不是文件更新。「更新 plan.md」不該成為任務——那是計畫自己的維護動作，寫進去會變成自我指涉的空轉。
- **未決事項不要藏**。spec 的開放問題、第三步沒問到的假設，全部進「風險與未定」，標 `[待確認]`，並註明它會擋住哪個任務。已經標成未決的事，就不要在別處偷偷選一個預設值當定案——要嘛整份計畫都當它未定，要嘛明說「暫以 X 進行，待確認後可能返工」。

### 第五步：寫檔並回報

`plan.md` 與來源 spec 放在同一層（`docs/<domain>/<feature>/plan.md`）。若檔案已存在，先讀它，問使用者要「更新既有計畫」還是「另開新檔」，不要直接覆蓋——既有 plan 可能已經有勾選過的進度。

寫檔後簡短回報：

- 檔案路徑
- 拆出幾個任務、預期執行順序的大致形狀
- 哪些 spec 需求這次不做
- 有哪些 `[待確認]` 會擋住執行
- 建議下一步（開始執行第一個任務，或先解掉某個未決事項）

## 為什麼這樣設計

- **verify 是必填欄位**：沒有驗證方式的任務，執行者只能自我宣告完成，plan 就退化成待辦清單。強制每條可驗證，plan 才能被別人（或另一個 session）接手。
- **先探查再拆解**：模型很容易套用自己熟悉的架構去拆任務，產出一份跟這個 repo 長得不像的計畫。先看 2～3 個既有實作，是最便宜的防呆。
- **不寫程式碼進 plan**：程式碼一旦寫進文件就開始腐爛，而且會讓執行者傾向照抄而非照著 repo 慣例寫。plan 指路，程式碼留在程式碼裡。
- **明確標「本次不做」**：範圍收斂的決定必須留下痕跡，否則下一個讀者會以為是漏掉的。

# Webhook 通知管道

## 概述

讓租戶可以登記自己的 HTTPS 端點，系統在事件發生時把通知以 HTTP POST 送到該端點，作為 email 之外的第二種送達方式。

## 背景與問題

目前只有 email 一種通知管道。前 20 大租戶中有 11 家自建了工單系統，他們現在的做法是設一個信箱收我們的通知再自己解析郵件內文，解析失敗率高、格式一改就壞。銷售端過去兩季有 4 筆案子因為「沒有 webhook」被列為缺件。

## 目標

- 租戶可自行登記 webhook 端點並開始收到通知，不需我們手動設定
- webhook 的送達可靠度不低於現有 email 管道
- 上線後半年內，前 20 大租戶有 8 家以上改用 webhook 取代信箱解析

## 非目標（範圍外）

- 不做 webhook 事件的過濾與訂閱（本次所有通知都送，不分事件類型）
- 不做租戶自訂 payload 格式
- 不取代 email 管道，兩者並存

## 使用者與情境

- **作為** 租戶的系統管理員，**我想要** 登記一個 HTTPS 端點接收通知，**以便** 直接進我們自己的工單系統而不用解析郵件
- **作為** 租戶的開發者，**我想要** 驗證收到的請求真的來自你們，**以便** 安全地信任 payload 內容

## 功能需求

| 編號 | 優先級 | 需求描述 |
|------|--------|----------|
| FR-1 | P0 | 租戶可登記一個 HTTPS webhook 端點；非 HTTPS 或格式不合法的 URL 應被拒絕 |
| FR-2 | P0 | 通知可經由 webhook 管道送出，送達與失敗的行為與現有 email 管道一致 |
| FR-3 | P0 | 每個請求帶有簽章標頭，租戶可用共享密鑰驗證請求確實來自本系統 |
| FR-4 | P0 | 對方回應 5xx 或逾時視為可重試失敗；回應 4xx 視為不可重試 |
| FR-5 | P1 | 租戶可在設定頁發送一則測試通知，立即看到成功或失敗與回應碼 |
| FR-6 | P2 | 提供近 7 天的送達成功率與失敗原因分佈 |

## 非功能需求

- **安全**：共享密鑰不得以明文出現在日誌；不得對內網位址發出請求（SSRF 防護）
- **效能**：單次送出的連線與讀取逾時合計不超過 10 秒
- **可觀測性**：送達成功／失敗數需與現有管道用同一套指標維度

## 驗收標準

- [ ] FR-1：Given 租戶輸入 `http://` 開頭的 URL，When 儲存設定，Then 被拒絕並提示需為 HTTPS
- [ ] FR-2：Given 租戶已登記端點，When 產生一則通知，Then 該端點收到 POST 且內容為渲染後的訊息
- [ ] FR-3：Given 收到一則 webhook，When 用共享密鑰重算簽章，Then 與標頭中的簽章相符
- [ ] FR-4：Given 對方回應 503，When 送出失敗，Then 依重試策略再試；Given 對方回應 400，Then 不再重試並記錄失敗
- [ ] FR-5：Given 租戶在設定頁按下「發送測試」，When 端點正常，Then 顯示成功與回應碼

## 相依與風險

- **相依**：租戶設定的儲存位置（目前租戶設定散在既有設定表）
- **假設**：租戶端點可承受與 email 相同的送出頻率
- **風險**：對方端點長期失效會持續消耗重試配額 → 需要失效後的處置方式

## 開放問題

- [ ] `[待確認]` 簽章要用哪種演算法與標頭格式？（HMAC-SHA256 與帶時間戳防重放是兩種常見做法，安全團隊尚未回覆）
- [ ] `[待確認]` webhook 的重試上限與退避參數要沿用 email 的設定，還是另訂？（webhook 對方是租戶自架服務，失效率預期較高）
- [ ] `[待確認]` 連續失敗多久後要自動停用該端點並通知租戶？

# 診斷：壞味道與 SOLID 違反

診斷的目標是**把「這段程式碼很亂」翻譯成具體的、可以逐條處理的問題**。說不出具體問題，後面的計畫就只能靠感覺。

## 五條原則，按優先序

順序是有意義的——它們會互相衝突，衝突時照這個順序讓步。

1. **SOLID** — SRP、OCP、LSP、ISP、DIP
2. **KISS** — 無聊而顯而易見，勝過聰明
3. **YAGNI** — 不為想像中的未來需求加抽象
4. **DRY** — 消除重複，但不要為了消除重複而過度抽象
5. **GoF 模式** — 只在它真的降低耦合或改善擴充性時才用

最常見的衝突是 DRY 對上 KISS：兩段程式碼長得像，抽成共用函式之後兩邊都得傳一堆旗標進去。**長得像不等於是同一件事**——它們如果會因為不同理由而各自改變，就該保持分開。這種情況 KISS 贏。

## SOLID 違反怎麼認

| 原則 | 違反的徵兆 | 具體問法 |
| --- | --- | --- |
| **SRP** 單一責任 | 一個類別因為兩種不同理由被改 | 誰會要求改這個類別？超過一種角色就違反了 |
| **OCP** 開放封閉 | 加一個新種類要改既有的 switch / if-else | 加第 N+1 種情況，要改幾個既有檔案？ |
| **LSP** 里氏替換 | 子類別覆寫方法後拋 `NotSupported`，或悄悄不做事 | 把子類別當父類別用，呼叫方會不會壞？ |
| **ISP** 介面隔離 | 實作者被迫寫一堆空方法 | 有沒有實作只用到介面的一半？ |
| **DIP** 依賴反轉 | 高層邏輯直接 new 出具體型別 | 要測這段邏輯，需不需要真的連資料庫？ |

**DIP 的測試問法最好用。** 「要測這段邏輯需不需要真的連外部系統」幾乎一問就中，而且答案直接指向要抽哪個介面。

## 壞味道對照

| 壞味道 | 徵兆 | 通常的解法 |
| --- | --- | --- |
| **God Object** | 一個類別知道太多、做太多，改什麼都要碰它 | 依責任拆分，先找出它服務的不同角色 |
| **Long Method** | 一個函式要捲畫面才看得完，或需要註解分段 | Extract Method；註解分段的地方通常就是切點 |
| **Feature Envy** | 一個方法一直在存取別的物件的資料 | Move Method 到資料所在的物件 |
| **Shotgun Surgery** | 一個小需求要改五個檔案 | 那五處的共同概念沒有被抽出來 |
| **Data Clumps** | 同一組參數反覆一起出現 | 抽成 value object |
| **Primitive Obsession** | 用 string/int 表達領域概念（訂單編號、金額） | 抽成有型別的 value object |
| **Divergent Change** | 一個類別因為多種不相干的理由被改 | SRP 違反，依變動理由拆分 |
| **Speculative Generality** | 只有一個實作的介面、沒人用的擴充點 | 刪掉（YAGNI） |
| **Message Chains** | `a.getB().getC().getD()` | Law of Demeter；把需要的東西直接暴露出來 |

最後一項容易被誤判——`builder.WithX().WithY()` 這種流暢介面不是 Message Chain，它每一步回傳的是同一個物件。判準是**你有沒有依賴中間物件的內部結構**。

## 什麼不算重構

診斷時常常會順手看到這些，要分清楚它們不屬於這次工作：

| 發現的事 | 為什麼不在這裡處理 | 去哪 |
| --- | --- | --- |
| 這段跑很慢 | 改了會動到行為的效能特性，測試無法歸因 | `performance-optimization`，另開一次提交 |
| 錯誤訊息很爛 / 沒處理錯誤 | 補錯誤處理是加行為 | 另開一次提交 |
| 這裡有 bug | 修 bug 會讓「測試該綠還是該紅」變得說不清 | 記下來，另開一次提交 |
| 缺測試 | 這是重構的**前置**，不是重構本身 | 步驟一先補 |
| 命名很爛 | **這個算**——純改名不動行為 | 就在這次做 |

看到不屬於這次的東西，**講出來但不要動手**。順手修會讓這次重構的驗證失去意義，而且會讓 review 的人分不清哪些改動是為了什麼。

## 判斷值不值得重構

不是所有難看的程式碼都該改。三個過濾：

1. **它會再被改嗎？** 三年沒動過而且沒人要動的程式碼，難看不構成成本。
2. **它擋住了什麼？** 說得出「因為這段的結構，加 X 功能要花三倍時間」比「它不符合 SOLID」有說服力得多。
3. **它快被刪掉了嗎？** 即將被取代的模組不要重構。

三項都指向不值得時，把診斷結果講出來就好，不要動手。**克制本身是判斷力的展現**，跟動手一樣重要。

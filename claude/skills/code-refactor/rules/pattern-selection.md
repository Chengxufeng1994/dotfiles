# 設計模式選型

## 唯一的判準

**這個模式解決哪個具體的結構摩擦？**

說得出來就用，說不出來就不用。「這裡適合用 Strategy」不算答案；「`ProcessPayment()` 的 switch-on-type 違反 OCP，每加一種支付方式都要改同一個函式」才算。

模式是**手段**，不是目標。一份用了五個 GoF 模式的重構，如果每個都說不出解決了什麼，那它比原本的爛程式碼更難維護——因為現在還多了五層間接。

## 從摩擦反查模式

不要從模式清單挑，要從症狀反查。

| 你觀察到的摩擦 | 候選模式 | 它實際解決什麼 |
| --- | --- | --- |
| 加一種新型別要改既有的 switch/if-else | **Strategy** | 每種演算法各自封裝，新增不動既有程式碼 |
| 建構邏輯複雜、或要依條件決定建哪一種 | **Factory / Abstract Factory** | 把「決定建什麼」跟「怎麼用」分開 |
| 狀態轉移散落在一堆布林旗標裡 | **State** | 每個狀態是一個物件，轉移變成明確的邊 |
| 要在不改原型別的前提下加行為 | **Decorator** | 層層包裝，組合取代繼承爆炸 |
| 一件事發生要通知多個不相干的對象 | **Observer** | 發布者不需要知道訂閱者是誰 |
| 多個子系統的呼叫順序很複雜且到處重複 | **Facade** | 一個入口封裝流程 |
| 演算法骨架相同、細節不同 | **Template Method** 或 **Strategy** | 骨架複用；能用組合就別用繼承 |
| 外部介面跟你要的形狀不合 | **Adapter** | 隔離外部變動，也是保持向後相容的工具 |
| 建構參數很多且多數可選 | **Builder** | 取代長參數列與多個建構子 |

**Template Method 與 Strategy 的選擇**：兩者都處理「骨架相同細節不同」。Template Method 用繼承，Strategy 用組合。**預設選 Strategy**——繼承把子類別綁死在父類別的生命週期上，而且一個類別只能繼承一次。只有在骨架真的穩定且變化點很多時，Template Method 才划算。

## 什麼時候不該用模式

| 情況 | 為什麼 |
| --- | --- |
| 只有一種實作，而且沒有第二種在路上 | Speculative Generality。等第二種出現再抽 |
| 用了之後讀的人要多跳三個檔案才看懂一件事 | 間接的成本超過解耦的收益 |
| 語言有內建的更簡單做法 | Go 的 function type 常常比一整套 Strategy 介面更合適；有一級函式就別為單方法介面建類別階層 |
| 只是為了讓程式碼「看起來專業」 | 這是最常見也最貴的理由 |

**三次法則**：同一種變化出現三次，才是抽象的門檻。第一次寫死，第二次注意到，第三次才抽。提早抽出來的抽象，八成會抽錯位置——因為你只看過一到兩個樣本。

## 命名

型別依**責任**命名，不依它在系統裡的角色或它的實作方式命名。

禁止 `Helper`、`Impl`、`Util`、`Manager`、`Processor`、`Handler` 這類字尾當作主要語意來源。它們的問題不是不好聽，是**它們什麼都不說**——`UserManager` 可能在做驗證、快取、持久化或以上全部。

取不出名字通常是設計訊號而非命名問題：**如果一個型別的責任講不清楚到可以命名，那它的責任就還沒切乾淨。** 回步驟三重新做物件導向分析。

| 差 | 好 | 為什麼 |
| --- | --- | --- |
| `UserManager` | `UserRepository` / `PasswordHasher` | 說出它到底做什麼 |
| `DataHelper` | `CsvRowParser` | 說出處理什麼、怎麼處理 |
| `PaymentProcessorImpl` | `StripePaymentProcessor` | 說出是哪一種實作 |
| `Utils` | 拆進各自的領域型別 | 這通常是雜物抽屜，不是型別 |

介面命名跟著語言慣例走：Go 用 `-er`（`Reader`、`PaymentProcessor`），C#/Java 常用 `I` 前綴。**跟著專案既有的做法**，不要引入第二套。

## 介面放哪裡

**介面屬於使用它的那一側，不是實作它的那一側。**

理由是依賴方向：介面放在消費端，實作端就會依賴消費端定義的契約，依賴指向穩定的那邊（DIP）。反過來把介面跟實作放在一起，消費端就得 import 實作套件，抽介面等於白抽。

Go 特別明顯——`package billing` 定義它需要的 `PaymentProcessor` 介面，`package stripe` 只管提供符合的具體型別，兩者之間沒有 import 關係。

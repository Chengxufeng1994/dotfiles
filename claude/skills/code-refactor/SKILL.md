# Code Refactor

重構的定義性限制是**保持外部行為**。這不是道德要求，是讓重構可驗證的唯一機制——測試綠燈就是契約：改完測試還是綠的，就證明你只動了結構。

這條契約也解釋了為什麼效能優化、錯誤處理改善、新功能不能搭便車。它們都會改變行為，一旦混進來，測試失敗你就分不出是重構壞的還是它們壞的，安全網就失效了。**它們不是不該做，是不該在同一批提交裡做。**

> **兩個入口。** 使用者可能直接說「幫我重構這段」而觸發本 SKILL，也可能透過 `/code-refactor` 命令進來。命令提供 17 點涵蓋清單與 8 階段交付序列——**它問「有沒有漏掉」**；本 SKILL 提供判準——**它問「該怎麼決定」**。從命令進來時不要重述它的清單，直接補上它只點名而沒展開的東西。

## 使用時機

- 程式碼會動但難讀、難改、難測，想在不改行為的前提下整理
- 有明確的壞味道要處理：God Object、超長函式、散彈式修改、重複邏輯、型別依賴過重
- 要套用 SOLID 或引入設計模式，但不確定哪個模式真的合適
- 加新功能前先整理，讓改動有地方落腳
- 要判斷某段程式碼值不值得重構

## Skill Boundaries

- 只想讓程式更好讀、不動結構 → 改用 `code-simplification`
- 效能問題 → 改用 `performance-optimization`。效能優化與重構要**分成不同提交**，理由見開頭
- 開分支、提交節奏、merge/rebase → 改用 `git-workflow`
- 上線策略、feature flag、rollback → 改用 `deployment-patterns`
- 系統層級的架構取捨（要不要拆微服務、換資料庫）→ 改用 `system-design`；決定了要留紀錄 → `architecture-decision-records`
- 本 SKILL 管 **一段既有程式碼在不改行為下的結構改善**：診斷、計畫、執行、驗證

## 流程

### 步驟一：確立安全網

```bash
# 跑專案的測試指令
```

**測試沒過或不存在，先處理它再談重構。** 沒有基線的重構是在賭，不是在改。

缺測試時先補**特徵測試**（characterization test）——不是驗證程式碼「應該」怎樣，而是把它**現在**的行為釘住，包含你覺得可疑的行為。重構的目的是保持現狀，不是順手修 bug；發現真的 bug 就記下來，另外開一次改動處理。

同時看清楚範圍：這段程式碼被誰呼叫、哪些是公開 API、動了會波及到哪。

語言專屬的重構手法另外載入：Go → `cc-skills-golang:golang-refactoring`。其他語言若有對應 skill 一併載入，沒有就只用本 SKILL。

### 步驟二：診斷

具體指出問題，不要停在「這段程式碼很亂」：

- 違反了哪一條 SOLID，為什麼
- 有哪些壞味道（God Object、Long Method、Feature Envy、Shotgun Surgery、Data Clumps、Primitive Obsession…）
- 責任與耦合問題，用白話講
- 現在的痛，跟程式碼長大後會變多痛

辨識方法與完整壞味道對照見 `rules/diagnosis.md`。

### 步驟三：物件導向分析

找出藏在程式碼裡的領域概念。這一步決定了後面所有改動切在哪裡——**切錯邊界的重構，套再對的模式也是白做**。

概念不會自己跳出來，用這五個探針去挖：

| 探針 | 怎麼看 | 挖出什麼 |
| --- | --- | --- |
| **參數群** | 哪幾個參數反覆一起出現、一起傳遞 | 一個沒被命名的概念（`startDate` + `endDate` → `DateRange`） |
| **命名前綴** | 同一個前綴的欄位或變數（`userEmail`、`userName`、`userTier`） | 前綴本身就是那個概念 |
| **註解分段** | 函式裡用來分段的註解 | 每一段是一個候選責任，註解文字通常就是型別名 |
| **分支的軸** | switch / if-else 是沿著什麼維度分的 | 那個維度是一個型別家族（付款方式、狀態、通知管道） |
| **測試的 setup** | 測這段邏輯要先準備什麼 | 準備得越多，代表真正的依賴越多——那些就是該抽介面的地方 |

最後一個探針最好用，因為它同時告訴你**該抽什麼**與**抽了之後測試會變多好寫**。

抽出候選概念後跑一次**領域語言檢驗**：把這些名字講給懂業務但不看程式碼的人聽，他聽得懂嗎？聽不懂的通常是技術產物而不是領域概念（`RequestContextWrapper` 是，`RefundPolicy` 不是）。技術產物也可以抽，但它們不該是主要的責任邊界。

這一步的產出是**概念清單，不是程式碼**。跳過它直接套模式，會得到「用了 Strategy，但三個 Strategy 其實是同一件事」這種結果——模式對了，切點錯了。

### 步驟四：提出計畫，取得同意

計畫要包含：改動順序、每一步服務哪條原則、用哪個**具名技法**、選了哪個 GoF 模式**以及為什麼它合適**、公開 API 若有變動怎麼維持相容。

用技法的名字寫計畫（Extract Function、Replace Conditional with Polymorphism、Introduce Parameter Object…），不要寫「把這裡改乾淨」。具名技法各有已知的安全操作序列，多數還有 IDE 自動化版本——自動的比手改安全，因為它會處理你會忘記的呼叫端。完整目錄與**執行順序（由淺入深）**見 `references/refactoring-techniques.md`。

模式選型邏輯與「什麼時候不該用模式」見 `rules/pattern-selection.md`。產出格式見 `templates/refactor-report.md`。

**大範圍重構要先讓使用者看過計畫再動手。** 重構會碰很多檔案，方向錯了成本很高。小範圍（單一函式、單一檔案）直接做。

### 步驟五：小步改，每步綠燈就提交

這是整個流程真正的安全機制：

```
改一小步 → 跑測試 → 綠燈 → 提交 → 下一步
                  └ 紅燈 → git reset --hard → 想清楚再來
```

每次提交都能編譯、都能通過測試。這樣任何一步出錯，損失上限是一個增量而不是整段工作。

有 IDE 的自動重構工具（rename、extract method）就用，它們比手改安全。

**這一步改到的註解與文件，跟程式碼放在同一個增量裡改完。** 型別改名、方法搬家之後，舊註解與 API 文件會描述一個不存在的結構——那比沒有註解更糟，因為讀的人會相信它。留到最後一起補一定會漏，因為那時你已經忘記哪些描述失效了。

### 步驟六：驗證

```bash
# 回歸測試（全部，不只改動的部分）
# 下游／整合測試：依賴這段程式碼的其他模組或服務
# 靜態分析：lint / vet / type check
# 效能敏感的路徑跑 benchmark 確認沒退步
```

**下游那一行不能省。** 單元測試綠燈只證明這個模組自己沒壞；重構動到的公開介面、序列化格式、錯誤型別，要靠整合測試才看得出有沒有波及呼叫方。步驟一盤點過的呼叫端就是這裡的檢查清單。

測試失敗就修實作，**絕不刪測試或跳過測試**。測試是你唯一的行為證據，關掉它等於關掉重構的意義。

**測試本身也要跟著整理**，這不違反上一句：

- 抽出來的新型別與新介面是新的接縫，值得補上針對它們的測試
- 原本針對「已經被抽走的私有邏輯」寫的測試，改成測新的公開單位，不是刪掉
- 測試裡的重複組裝（setup、fixture）跟production 程式碼一樣適用 Extract

差別在於：**改測試的結構可以，改測試的斷言不行。** 斷言是行為契約，動了它就不再是重構。

benchmark 這裡的目的是**確認沒有退步**，不是追求進步——想讓它更快是另一件事，見 Skill Boundaries。

### 步驟七：確認做完了，交出前後對照

**重構沒有自然終點**——「還可以更乾淨」永遠成立，所以停手是一個要主動下的判斷，不是等它自己發生。四個訊號代表該收手：

- **步驟二列的問題都處理完了。** 回頭對那份清單，不要即興追加當時沒診斷出來的項目。想追加就是下一輪的事
- **繼續改的理由從「這樣解決 X」變成「這樣比較漂亮」。** 說不出解決什麼就是到了
- **新加的間接層開始需要解釋。** 要跟讀者說明「這裡為什麼多一層」，代表那層的成本已經超過收益
- **測試開始變難寫。** 這個訊號最可靠：重構的方向對的話，測試會越來越好寫。變難代表你把邊界切在錯的地方，往回退一步

反過來，**還不能停**的訊號只有一個：步驟一建立的測試現在是紅的，或有任何一步提交是不能編譯的。那不是「做完了」，是「做壞了」。

確認做完之後，用 `templates/refactor-report.md` 的對照表，說明在可測試性、可擴充性、可讀性、依賴穩定性上的變化。

誠實列出這次重構的代價：多了幾個檔案、多了一層間接、新人要多理解什麼。**只有好處的重構不存在**，講不出代價通常代表抽象加過頭了。

## 規則

- IMPORTANT：**沒有測試基線就不要開始。** 缺測試先補特徵測試釘住現況——重構要保持的是現在的行為，不是應該有的行為。
- IMPORTANT：**每一步提交都要能編譯、能過測試。** 這是「出事只損失一個增量」的前提，也是重構跟大爆炸改寫的唯一差別。
- IMPORTANT：**選模式要說得出它解決哪個具體摩擦。** 「這裡適合用 Strategy」不夠，要能說「`ProcessPayment()` 的 switch-on-type 違反 OCP，加一種支付方式就得改同一個函式」。說不出來就不要用。
- IMPORTANT：**公開 API 有變動就提供 Adapter 或 Wrapper**，並標記成日後可廢棄。重構不該逼呼叫方跟著改。
- IMPORTANT：**型別依責任命名，禁止 `Helper`、`Impl`、`Util`、`Manager` 這類模糊字尾。** 取不出名字通常代表責任還沒切乾淨——那是設計訊號，不是命名問題。
- NEVER：**不可刪除或跳過測試來讓建置通過。** 測試紅燈是資訊，不是障礙。
- NEVER：**不可在重構的提交裡混入效能優化、錯誤處理改善或新功能。** 混了之後測試失敗就無法歸因，安全網失效。要做就另外開一次提交。
- NEVER：**不可為了只出現一次的情況加抽象**（YAGNI）。三次才是抽象的門檻。
- NEVER：**不可順手修 bug。** 發現了就記下來另外處理——重構的驗證前提是行為不變，修 bug 會讓測試該紅還是該綠變得說不清。
- NEVER：**不可改測試的斷言。** 整理測試的結構（抽出 setup、更新被搬走的目標）可以，但斷言是行為契約，動了它就不再是重構。

### 邊界情況

- **完全沒有測試而且補不出來**（例如重度依賴外部系統）→ 說明風險並問使用者要不要繼續。真要做就縮到最小範圍，用 IDE 的自動重構工具，每步人工驗證
- **重構到一半發現需求其實會變** → 停下來。針對即將到來的需求重構，比針對想像中的完美結構重構有價值得多
- **這段程式碼即將被刪掉或取代** → 不要重構。確認它的壽命再決定
- **使用者只要診斷不要動手** → 只做步驟一到四，交出診斷與計畫，不改任何程式碼
- **範圍大到一次做不完** → 切成幾輪，每輪自己是完整的（可編譯、測試過、有價值）。不要留下改到一半的中間狀態

## 資料夾結構

```
code-refactor/
├── SKILL.md
├── rules/
│   ├── diagnosis.md          # 步驟二，壞味道與 SOLID 違反的辨識方法
│   └── pattern-selection.md  # 步驟四，GoF 選型與不該用模式的情況
├── references/
│   └── refactoring-techniques.md  # 步驟四寫計畫、步驟五執行時的技法目錄與順序
└── templates/
    └── refactor-report.md    # 步驟四出計畫、步驟七出對照時的格式
```

三份的分工是一條線：`diagnosis` 說**哪裡不對**、`refactoring-techniques` 說**動作叫什麼名字**、`pattern-selection` 說**目標架構長怎樣**。診斷完直接跳到模式，會得到套了模式但切錯邊界的結果。

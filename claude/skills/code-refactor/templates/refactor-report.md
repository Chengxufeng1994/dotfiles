# 重構產出格式

兩個地方會用到：**步驟四**出計畫（動手前），**步驟七**出對照（做完後）。

## 步驟四：重構計畫

```markdown
## 診斷

- **[問題名稱]**：[具體位置與症狀]。違反 [SOLID 哪一條]，因為 [原因]。
  現在的成本：[具體的痛，例如「加一種支付方式要改 4 個檔案」]

## 物件導向分析

現在混在一起的概念：
- [概念 A] — 目前散在 [哪裡]
- [概念 B] — 目前跟 [概念 A] 綁在同一個型別裡

建議抽出：
- `[型別名]` — 責任是 [一句話]
- `[介面名]` — 由 [誰] 消費，[誰] 實作

## 計畫

1. **[改動]** — 服務 [哪條原則]；[用哪個模式，解決哪個摩擦]
2. ...

向後相容：[公開 API 有沒有變動；有的話 Adapter 怎麼做，標記何時可移除]

## 結構草圖

[UML 文字圖，見下方寫法]
```

**計畫要能被否決。** 每條改動都寫出「服務哪條原則、解決哪個摩擦」，使用者才有辦法說「這條不必」。只列出要做什麼，他只能全收或全退。

### UML 文字圖寫法

```
┌─────────────────────┐        ┌────────────────────────┐
│ <<interface>>       │        │ StripePaymentProcessor │
│ PaymentProcessor    │◄╌╌╌╌╌╌│ + Process() error      │
│ + Process() error   │        └────────────────────────┘
└─────────────────────┘        ┌────────────────────────┐
          ▲                    │ PayPalPaymentProcessor │
          │ 使用               │ + Process() error      │
┌─────────────────────┐        └────────────────────────┘
│ CheckoutService     │                    ╎
│ - processor         │◄╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╯
└─────────────────────┘
```

關係符號：`-->` 關聯、`..>` 依賴、`--|>` 繼承、`..|>` 實作。

圖只畫**這次重構會動到的型別**。把整個模組畫出來會淹沒重點——讀者要看的是變化，不是全貌。型別超過六七個就別畫圖了，改用條列說明關係。

## 步驟七：前後對照

```markdown
## 前後對照

| 面向 | 之前 | 之後 |
|---|---|---|
| 可測試性 | [具體：例如「要測結帳得起一個 Stripe sandbox」] | [具體：例如「注入 fake processor 即可」] |
| 可擴充性 | [加一種支付方式要改 4 個檔案] | [新增一個型別，不動既有程式碼] |
| 可讀性 | [`Checkout()` 240 行，混了驗證、計價、扣款、通知] | [四個型別各一個責任，最長 45 行] |
| 依賴穩定性 | [直接依賴 stripe-go] | [依賴自訂介面，SDK 換掉不影響領域邏輯] |

## 這次的代價

- [多了幾個檔案／多了一層間接／新人要多理解什麼]
- [有沒有留下相容層要日後清掉]

## 驗證

- 回歸測試：[結果]
- 靜態分析：[結果]
- Benchmark（如果跑了）：[確認沒退步]
```

**表格兩欄都要寫具體事實，不要寫評語。** 「之前：耦合高／之後：耦合低」等於沒說——讀的人無法判斷是真的改善還是自我感覺良好。寫「之前要起 sandbox 才能測／之後注入 fake 就好」，改善是可驗證的。

**「這次的代價」不能省。** 只有好處的重構不存在。列不出代價通常代表抽象加過頭了——回頭看是不是有哪個介面只有一個實作。

## 使用者只要診斷時

只出步驟四的「診斷」與「物件導向分析」兩節，附一句建議的優先序，不出計畫也不動程式碼。他要的是判斷依據，不是待辦清單。

## 填好的實例

情境：`NotificationService.Send()` 一個函式 180 行，switch 在通知管道上（email / sms / push），每個分支各自帶了一份重試迴圈，而且三處都在傳同一組 `(recipient, subject, body, locale)`。

### 步驟四交出的計畫

```markdown
## 診斷

- **OCP 違反**：`Send()` 的 switch-on-channel。加一種管道（目前 Slack 在路上）要改這個
  函式、它的測試、以及三處重試迴圈其中一處。現在的成本：上次加 push 花了兩天，其中
  一天在追為什麼 push 的重試次數跟另外兩個不一樣
- **Data Clumps**：`(recipient, subject, body, locale)` 在 11 個函式簽名裡一起出現
- **重複邏輯**：重試迴圈三份，已經漂移——email 遇到 429 會重試，sms 不會

## 物件導向分析

探針結果：
- 參數群 → `(recipient, subject, body, locale)` 是一個沒被命名的概念
- 分支的軸 → switch 沿著「送達方式」分，那是一個型別家族
- 測試 setup → 測 `Send()` 要 mock 三個 SDK，因為它直接 new 出來

抽出：
- `Notification` — 要送的東西（收件人、內容、語系）。領域語言檢驗：業務聽得懂 ✓
- `Channel` 介面 — 送達方式。由 `NotificationService` 消費，三個具體型別實作
- ~~`RetryPolicy` 介面~~ — **不抽**。目前只有一種策略，第二種也沒在路上（YAGNI）。
  重試邏輯抽成一個共用函式即可，等真的出現第二種策略再談介面

## 計畫

1. **Introduce Parameter Object** → `Notification`。服務 DRY；11 個簽名收斂成 1 個參數
2. **Extract Function** → 把三份重試迴圈抽成一個 `withRetry()`。服務 DRY；順帶修掉
   已經漂移的 429 行為不一致（**這是行為變更，另開一次提交**）
3. **Replace Conditional with Polymorphism** → `Channel` 介面 + 三個實作。服務 OCP；
   加 Slack 只需新增一個型別

順序是淺到深：1 和 2 不動型別結構，做完之後 3 的切點會更清楚。

向後相容：`Send(recipient, subject, body, locale)` 保留為薄包裝轉呼叫新簽名，標記
3.0 移除。

## 結構草圖

┌──────────────────────┐        ┌──────────────────┐
│ NotificationService  │───────►│ <<interface>>    │
│ - channels map       │        │ Channel          │
│ + Send(Notification) │        │ + Deliver() error│
└──────────────────────┘        └──────────────────┘
                                     ▲    ▲    ▲
                              EmailChannel │ PushChannel
                                      SmsChannel
```

### 步驟七交出的對照

```markdown
## 前後對照

| 面向 | 之前 | 之後 |
|---|---|---|
| 可測試性 | 測 `Send()` 要 mock 三個 SDK，因為它直接 new | 注入 fake Channel；SDK 只在各自的 channel 測試裡出現 |
| 可擴充性 | 加一種管道要改 `Send()`、它的測試、其中一份重試迴圈 | 新增一個實作 `Channel` 的型別，`Send()` 不動 |
| 可讀性 | 單一函式 180 行，三種管道的細節交錯 | `Send()` 22 行；每個 channel 40-55 行，各自獨立 |
| 依賴穩定性 | 直接依賴三個 SDK 套件 | 依賴自訂 `Channel` 介面；換 SDK 不影響派送邏輯 |

## 這次的代價

- 多了 5 個檔案（1 介面 + 3 實作 + 1 value object）
- 追一則通知的完整路徑要多跳一層
- 留下 `Send(recipient, ...)` 相容層，3.0 要記得清掉

## 驗證

- 回歸測試：全數通過（含新增的 `Notification` 建構驗證測試）
- 下游整合：billing 與 auth 兩個呼叫方的整合測試通過
- 靜態分析：無新增警告
```

這個例子值得注意的是**第三個抽象被拒絕了**。`RetryPolicy` 看起來跟 `Channel` 一樣合理——都是「一種策略」——但只有一個實作而且沒有第二個在路上。計畫裡明寫拒絕的理由，比安靜地不做更有價值：它讓下一個人知道這件事被考慮過，以及在什麼條件下該重新考慮。
